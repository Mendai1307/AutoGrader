# 一、赛事要求解析

## 1.1 赛题原文对 AutoGrader 的定义

AutoGrader：支持计算机专业实验报告自动解析、评分点逐项核查与成绩评语智能生成的智能评阅教学平台。（方向一 · 参赛小项原文）

三句定语就是三条必答题，也是评分的锚点：

| 原文定语 | 必答题 | 落到产品上 |
|---|---|---|
| 实验报告自动解析 | 报告里的文字、代码、截图，你能不能真的读懂？ | 多模态解析：章节结构树 + 代码识别 + 图表定位 |
| 评分点逐项核查 | 你是不是逐个评分点找证据、给判定？ | Rubric 驱动的逐项「评分点—证据—判定—理由」四元组 |
| 成绩评语智能生成 | 除了分数，有没有给学生可执行的话？ | 个性化、非模板化、可追溯到证据的评语 |

## 1.2 硬性约束（不可协商）

| # | 约束 | 原文要点 | 对项目的硬性含义 |
|---|---|---|---|
| C1 | 平台唯一 | 「以 LearnBuddy 平台为赛事唯一指定平台」 | AI 能力必须由 LearnBuddy 承载 |
| C2 | 必须在线 | 「作品须部署至浏览器环境，提供可直接访问的在线链接」 | 交付物里必须有一个评委点得开的 URL |
| C3 | 必须开源 | 「须提交完整的源代码仓库（GitHub/Gitee 链接）」 | 仓库要 clone 下来就能跑，依赖越少越好 |
| C4 | 必须留痕 | 「需提交 LearnBuddy 历史对话记录作为评审参考」 | 对话记录是 AI 能力的唯一合法证明，必须厚且可追溯 |
| C5 | 工期紧 | 初赛 10 天开发期，决赛 1 周完善期 | 初赛不追求生产级系统 |
| C6 | 禁止代劳 | 「禁止使用 AI 生成完整方案后直接提交（AI 是工具，不是替代者）」 | 对话记录要体现人的决策与多轮迭代，不是一次性生成 |
| C7 | 原创 | 禁止抄袭搬运；第三方库需注明 | 复用自有赛前资产需如实说明边界 |
| C8 | 形态合法 | 「智能体可以是 web demo，也可以是专家智能体」 | 两条路都合规 → 两条都走，互为佐证 |

C8 是本次立项的战略支点：赛事规则明确认可「专家智能体」这一形态。这给了我们一个别的队伍很少走的路——同一套能力，交两份互相印证的证据。

## 1.3 评审规则与权重

包括技术创新性、工程完整性、AI 工具使用、用户体验，满分 100 分。

| 评分维度 | 分值 | 官方评审要点 | 本项目对应解读 |
|---|---|---|---|
| 技术创新性 | 30 | AI 能力应用的深度与独特性 | 是不是"调个大模型打个分"？评阅的认知过程有没有被工程化？ |
| 工程完整性 | 25 | 代码质量、架构设计、功能完备性 | clone 能不能跑？契约稳不稳？数据自不自洽？功能闭环了没有？ |
| AI 工具使用 | 25 | LearnBuddy 使用深度 | 用了多深、用了多少、证据能不能被直接验证 |
| 用户体验 | 20 | 界面设计、交互流畅度、功能可用性 | 评委 3 分钟能不能看懂价值、5 分钟能不能自己动手 |

加分项（总分外）

| 加分项 | 分值 | 条件 | 本项目对策 |
|---|---|---|---|
| 社交媒体传播 | +1 | 过程设计完整，不能是几句话 + 2-3 张图 | 连载式开发日志（选题 → 架构 → 踩坑 → 数据） |
| 跨专业组队 | +2 | 团队成员来自 2 个及以上不同专业/院系 | 作品介绍 PPT 必须含团队成员信息，否则此项直接归零 |

## 1.6 合规红线

禁止抄袭、搬运他人作品

禁止使用 AI 生成完整方案后直接提交（AI 是工具，不是替代者）

# 二、评审维度 → 设计原则（反向推导）

评分标准不是评分时才用的尺子，而是开工前就要刻进设计里的模具。

| 维度 | 分值 | 评委心里真正的问题 | 我们必须拿出的"可验证证据" |
|---|---|---|---|
| 技术创新性 | 30 | 「这和直接用 ChatGPT 打分有什么区别？」 | ① 五 Agent 评阅流水线（逐环可溯源）② 契约驱动的结果闭环 ③ AI vs 教师金标准的量化一致性报告 |
| 工程完整性 | 25 | 「clone 下来能跑吗？数据是真的吗？」 | ① 一键构建脚本 ② 构建期双端校验（前端契约 + 工具链六项）③ 文档与实现一致 |
| AI 工具使用 | 25 | 「你说用了 LearnBuddy，我怎么知道用了多深？」 | ① 专家智能体本体 ② 编号可查的对话记录索引 ③ 网页深链唤起智能体的现场演示 |
| 用户体验 | 20 | 「打开链接 3 分钟，我看到了什么？」 | ① 首屏价值主张 + 演示入口 ② 逐项证据可点开 ③ 上传新报告有真实即时反馈 |

贯穿全部四维度的一条主线：可追溯（Traceability）。每一条结论都能回答"你凭什么这么说"，并且点两下就能看到凭据。

## 3.2 缺口（决定"重生"要做的事）

| 缺口 | 影响维度 | 严重度 |
|---|---|---|
| 形态 A「实验报告评阅专家」LearnBuddy 专家智能体包 —— **部分构建**：Prompt / Skills / Tools 三层已落地、ReviewResult 契约已冻结；**Workflow / Evaluation / 打包层未完成** | AI 工具使用（25 分） | 🟠 高 |
| 3 分钟 Demo 视频 —— 缺失 | 提交必需项 | 🔴 致命 |
| 作品介绍 PPT —— 缺失（连带丢失"跨专业组队 +2"） | 提交必需项 + 加分 | 🔴 致命 |
| LearnBuddy 使用记录需以真实对话 ID / 轮次 ID 入库并重算指纹 | AI 工具使用 + 工程完整性 | 🟠 高 |
| 纯静态架构下"用户上传新报告→重新评分"能力受限 | 用户体验 | 🟡 中 |

## 3.3 必须继承的架构范式：Compile-time AI

【常规做法·Runtime AI】 【本项目·Compile-time AI】用户上传 → 浏览器 → 后端 → 第三方 LLM → 数据库 开发时：LearnBuddy 对话中上传报告 ↑ 违反"平台唯一"约束 → 五 Agent 流水线推理 → 产出 ReviewResult JSON → 入库 运行时：浏览器 → 读仓库内 JSON → 确定性渲染 + 规则核查 ↑ 零 AI 调用、零后端这个范式不是妥协，而是本赛题约束下唯一能同时满足「以平台为载体」与「必须有在线链接」的解，并额外换来三个好处：结果可复现、过程可审计、质量可评测。
