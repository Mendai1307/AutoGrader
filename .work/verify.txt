AutoGrader 项目目标定义书
赛事：深大计软 & 腾讯云 · 粤港澳大湾区 AI Coding 创新大赛（LearnBuddy 版）
赛道：AI 应用创新大赛　|　选题：方向一「AI + 教学管理助手」→ AutoGrader
平台：LearnBuddy（赛事唯一指定平台）
版本：v1.0（立项稿）　|　日期：2026-09-25
本文件回答一个问题：在本次赛事里，AutoGrader 要成为什么，才算赢。
全文按「赛事要求 → 评审反推 → 现状 → 目标 → 边界 → 倒排」展开，每个目标都绑定可检验的验收标准与证据。
一、赛事要求解析
1.1 赛题原文对 AutoGrader 的定义
AutoGrader：支持计算机专业实验报告自动解析、评分点逐项核查与成绩评语智能生成的智能评阅教学平台。（方向一 · 参赛小项原文）
三句定语就是三条必答题，也是评分的锚点：
--- TABLE ---
原文定语 | 必答题 | 落到产品上
实验报告自动解析 | 报告里的文字、代码、截图，你能不能真的读懂？ | 多模态解析：章节结构树 + 代码识别 + 图表定位
评分点逐项核查 | 你是不是逐个评分点找证据、给判定？ | Rubric 驱动的逐项「评分点—证据—判定—理由」四元组
成绩评语智能生成 | 除了分数，有没有给学生可执行的话？ | 个性化、非模板化、可追溯到证据的评语
--- /TABLE ---
1.2 硬性约束（不可协商）
--- TABLE ---
# | 约束 | 原文要点 | 对项目的硬性含义
C1 | 平台唯一 | 「以 LearnBuddy 平台为赛事唯一指定平台」 | AI 能力必须由 LearnBuddy 承载
C2 | 必须在线 | 「作品须部署至浏览器环境，提供可直接访问的在线链接」 | 交付物里必须有一个评委点得开的 URL
C3 | 必须开源 | 「须提交完整的源代码仓库（GitHub/Gitee 链接）」 | 仓库要 clone 下来就能跑，依赖越少越好
C4 | 必须留痕 | 「需提交 LearnBuddy 历史对话记录作为评审参考」 | 对话记录是 AI 能力的唯一合法证明，必须厚且可追溯
C5 | 工期紧 | 初赛 10 天开发期，决赛 1 周完善期 | 初赛不追求生产级系统
C6 | 禁止代劳 | 「禁止使用 AI 生成完整方案后直接提交（AI 是工具，不是替代者）」 | 对话记录要体现人的决策与多轮迭代，不是一次性生成
C7 | 原创 | 禁止抄袭搬运；第三方库需注明 | 复用自有赛前资产需如实说明边界
C8 | 形态合法 | 「智能体可以是 web demo，也可以是专家智能体」 | 两条路都合规 → 两条都走，互为佐证
--- /TABLE ---
C8 是本次立项的战略支点：赛事规则明确认可「专家智能体」这一形态。这给了我们一个别的队伍很少走的路——同一套能力，交两份互相印证的证据。

四、项目目标定义
4.0 总目标
**把 AutoGrader 做成「一个由 LearnBuddy 专家智能体真实驱动的计算机专业实验报告智能评阅系统」——
教师用自然语言定义评分点，智能体完成多模态解析 → 逐项证据核查 → 二次复核 → 成绩与评语生成，
产出可追溯、可复现、可评测的评阅结果；并以在线 Web 平台承载产品化界面与完整证据链，
形成「专家智能体（能力本体）+ Web Demo（产品形态）」双形态交付。**
一句话版本（对内对齐用）：
AI 跑在 LearnBuddy 里，产品放在浏览器里，证据留在仓库和对话记录里。
4.1 技术创新性（30 分）
目标：让"AI 评阅"从一次模型调用升级为一套可检验的评阅工艺。
--- TABLE ---
# | 关键举措（技术主张） | 为什么要这么做（评审视角）
T1 | 五 Agent 评阅流水线：Parser → Evidence → Grader → Reviewer → Feedback，逐环输出置信度与原文证据引用 | 直接回答"和直接问大模型有什么区别"——区别在于过程可见
T2 | 契约驱动闭环：一份 Zod ReviewResult 同时约束智能体输出格式、前端类型、仓库数据 | 三处同源，杜绝"演示数据 vs 真实数据"的质疑
T3 | 证据强制回链：无证据不得高置信，违反即契约校验失败 | 把"AI 不能瞎说"从口号变成可执行的校验规则
T4 | Compile-time AI 范式：AI 推理前移到开发时，运行时零 AI 调用 | 在"平台唯一 + 要在线链接"的夹缝中给出的原创解法
T5 | AI vs 教师金标准一致性评测：逐项命中率、总分 MAE、置信度校准 | 把评委必问的"AI 靠不靠谱"变成一页数据结论（v0.1 已得 MAE 3.05，并主动披露差档 8.00）
--- /TABLE ---
验收标准
[ ] 五 Agent 流水线的每一环，都能在 /trace 页看到该环的输入、输出与置信度变化
[ ] 任意一份 ReviewResult JSON 都通过契约校验、总分复算、指纹复算三重校验
[ ] /eval 页展示 AI vs 金标准的量化一致性，且指标可由页面上的原始数据复算
[ ] 至少一处"主动披露局限"（如差档 MAE 偏高），证明评测不是自吹
证据清单：/trace 溯源页 · /eval 评测页 · docs/contract.md · docs/testing.md
4.2 工程完整性（25 分）
目标：让评委克隆下来就能跑，让数据自己证明自己没造假。
--- TABLE ---
# | 关键举措 | 验收口径
E1 | 单人可复现的构建路径：git clone → 安装 → build → preview | 在干净环境按 README 逐条执行，零错误
E2 | 构建期三重校验：契约（zod）/ 总分复算 / 指纹复算 | 全部通过；任一失败即构建失败（fail-fast）
E3 | 依赖白名单：禁止第三方 AI SDK 进入依赖树 | package.json 中无 openai / anthropic / langchain-*
E4 | 交付物齐全度：链接 / 视频 / PPT / 仓库 / 对话记录 5/5 | 提交清单逐项打勾，无"待补"
E5 | 文档与实现一致（v0.1 审查曾发现 README 与实测不符） | 文档中每条断言都有对应的实测记录
E6 | 前端"一条命令本地跑"作为最后兜底 | 断网环境下也能本地验收演示
--- /TABLE ---
验收标准
[ ] 5 项必交材料全部齐备
[ ] 主链接线上实测 HTTP 200，且 12 个报告页全部可达
[ ] 仓库根目录 README 首屏即给出：在线链接、3 条启动命令、目录导航、对话记录索引
证据清单：GitHub 仓库 · CI 工作流 · 构建日志 · README 验收记录
4.3 AI 工具使用（25 分）—— 本阶段最高性价比
目标：让 LearnBuddy 的使用深度可验证，而不是"我们用了 AI"。
--- TABLE ---
# | 关键举措 | 说明
A1 | 构建形态 A：LearnBuddy「实验报告评阅专家」专家智能体（本次重生核心） | 注入评分方法论、Rubric 模板、样例库、固定输出契约；教师可直接对话、上传报告获得真实评阅
A2 | 对话记录即核心资产：一条主线对话 + 每份报告一条 + 每个 Agent 一条 | 迭代过程完整保留，不删历史；索引写入仓库
A3 | 真实溯源字段：每条结果 JSON 带真实 sourceConversationId + sourceTurnId | 评委可顺着 ID 找到那一轮对话
A4 | 网页 ↔ 智能体双向耦合：Web 端深链唤起（learnbuddy://task?action=start&prompt=...） | 把"构建期固化的结果"升级为"现场可交互复现"，是本维度最强的加分动作
A5 | 方法论 Skill 化：把评阅流程沉淀为可复用 Skill | 对应赛事亮点「Skills 技能加持」「校级 AI 资产沉淀」
--- /TABLE ---
验收标准
[ ] 专家智能体可被评委当场对话验证：给它一份新报告，它能输出符合契约的评阅结果
[ ] 仓库内对话记录索引 ≥ 10 条，条目与结果 JSON 一一对应
[ ] /grade 或 /report/[id] 页上的"用评阅专家重跑"按钮，点击可拉起 LearnBuddy 并预填上下文
[ ] 深链不可用时有三层降级（L0 深链 / L1 剪贴板兜底 / L2 静态结果页），不出现死按钮
证据清单：专家智能体 · conversations/ 对话归档 · 深链演示 · docs/learnbuddy-usage.md
风险提示：A4 依赖的是客户端自定义协议（逆向发现、非官方开放 API）。定位为增强项，不作为核心闭环的唯一起点；必须在 PPT 中把合规表述写清——它是操作系统级的用户主动唤起，不是 API 调用、不绕过授权、不自动执行。
4.4 用户体验（20 分）
目标：评委打开链接后 3 分钟看懂价值、5 分钟能自己动手。
--- TABLE ---
# | 关键举措 | 说明
U1 | 三段式信息架构：先结论（总分/等级/一键下载）→ 再证据（逐项四元组）→ 再方法（流水线溯源 + 一致性评测） | 让"结论"和"依据"分层，不做信息倾泻
U2 | 逐项证据可点开：每个评分点都能展开看到命中原文高亮 | 可解释性是本产品的核心体验
U3 | 上传新报告 → 即时真实反馈：浏览器端确定性核查器立刻给出章节完整性、代码 API 核查、统计特征、查重结果；语义部分明确标注"由 LearnBuddy 评阅专家生成"并给出入口 | 用"真实运行的非 AI 部分"补上"静态 Demo 不够真"的裂缝
U4 | 置信度可视化：低置信/需人工复核的项有明确视觉标识与复核建议 | 体现"AI 辅助而非替代教师"的产品伦理
U5 | 首屏 3 秒法则：一句价值主张 + 一个可直接点的演示入口 | 评委不会替你找入口
--- /TABLE ---
验收标准
[ ] 首屏无滚动即可看到：价值主张、双形态入口、在线可达状态
[ ] 核心路径（首页 → 工作台 → 报告详情 → 溯源）零死链、无空白页
[ ] 上传一份新报告后，5 秒内出现客观核查结果
[ ] 移动端宽度下布局不破版
证据清单：录屏 / Demo 视频 · 线上链接 · /grade 工作台
4.5 明确不做（Scope Out）
明确写下"不做什么"，本身是工程判断力的体现，也是控制 36 小时风险的关键。
--- TABLE ---
不做 | 原因
实时 LLM 评分的后端服务 | 违反"平台唯一"约束；且运行时不需要

6.3 关键契约备忘（实施时极易踩坑）
总分口径必须写成：总分 = Σ (score / maxScore) × weight，而不是 Σ (score × weight / 100)。
原因：各评分点的 maxScore 是教师自定标度（5 / 10 / 15 / 20 不等），标度大小不影响占比，占比只由 weight 决定。若 Prompt 中不显式写清口径与权重序列（5/12/5/7/20/10/11/13/7/5/3/2），模型极易按错误口径算总分，产物会在指纹校验环节失败。
七、一句话结论
交付的不是"一个能调大模型的网站"，而是"一个由 LearnBuddy 专家智能体真实驱动的评阅系统，以及它的产品化界面与完整证据链"。
四个维度其实在问同一件事：你说的每一句话，能不能被验证。 技术创新性问"过程能不能被看见"，工程完整性问"结果能不能被复算"，AI 工具使用问"对话能不能被追溯"，用户体验问"评委能不能自己上手验证"。把"可追溯"做到极致，四个维度一起涨。
