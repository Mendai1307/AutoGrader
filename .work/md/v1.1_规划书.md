# 零、最终目标（冻结）

一个由 LearnBuddy 专家智能体真实驱动的计算机专业实验报告评阅系统。

| # | 交付物 | 角色 | 具体产出 |
|---|---|---|---|
| 一 | 专家智能体包 | 能力本体（AI 在这里跑） | Prompt + Skills + Tools + Workflow + Evaluation 五件套 |
| 二 | Web Demo 产品展示页 | 产品形态 | 在线可访问链接 + 源码仓库 |
| 三 | 评审材料包 | 佐证链 | 作品介绍 PPT / 3 分钟演示视频 / LearnBuddy 对话记录归档 |

三部分不是三个独立作品，而是同一个能力的三种呈现：能力本体（一）驱动产品界面（二），产品界面产生可验证的痕迹（三）。三者共用同一个 ReviewResult 契约。

# 路径 0：前置冻结（所有后续步骤的依赖根）

路径 0 不产出功能，只冻结不变式。这五项不冻死，后面每一步都会返工。

| 步骤 | 内容 | 产物 | 完成判据 |
|---|---|---|---|
| 0.1 | 冻结 ReviewResult 契约 | JSON Schema（`contract/`）+ 契约说明文档（`docs/contract.md`） | 12 份既有结果全部通过契约校验 |
| 0.2 | 冻结 Rubric 与权重 | R1–R12 定义 + 权重序列 | 权重和 = 100；每项 maxScore 与档位系数明确 |
| 0.3 | 冻结总分口径与指纹算法 | 计算函数 + 口径说明 + 指纹实现（Python / JS 双侧） | 总分复算、指纹复算对 12 份样例全部相等（含跨语言一致） |
| 0.4 | 冻结目录结构与命名规范 | 目录骨架 | 三部分产物各有唯一落点，命名可被机器识别 |
| 0.5 | 建立对话归档规范 | 归档模板 + 索引表 | 每条对话可定位到：日期 / 目的 / 结论 / 产物 / 对话 ID |

## 0.6 写死的核心口径（不得改写）

总分 = Σ (score / maxScore) × weight —— 不是Σ (score × weight / 100)。

原因：各评分点的 maxScore 是教师自定标度（5 / 10 / 15 / 20 不等），标度大小不影响占比，占比只由 weight 决定。

权重序列（和 = 100）：5 / 12 / 5 / 7 / 20 / 10 / 11 / 13 / 7 / 5 / 3 / 2。

# 路径一：专家智能体包（Prompt + Skills + Tools + Workflow + Evaluation）

## 1.0 三模式总览（Skill 落点）

教师输入 → `S0` 判断意图 → 分三类模式。三模式分**两组**：

| 组 | 模式 | 链路 | 涉及 Skill |
|---|---|---|---|
| 生产组（决定分数） | **1 建标** | `T6 给候选样板 → 教师选 → S1 构建 → S5 自检 → 保存` | S1（依赖 T6） |
| 生产组（决定分数） | **2 评阅** | `S2 解析 → S3 取证与判定 → S4 计算 →〔教师复核〕→ S6 评语 → 输出` | S2 / S3 / S4 / S6（+ S5 横向） |
| 消费组（只读，不改任何判定） | **3 复核** | `已有 ReviewResult → S7 入口 B 解释回放 → 无后置` | S7（入口 B） |

三条补充规则：

- `S5 结构装配与自检` **横向贯穿模式 2** 全链，对内对应 Reviewer 环，**不对教师暴露**
- `S7 入口 A（复核清单）` 服务于**模式 2 内**的教师复核节点；教师若参与，终判分**回灌 S4 重算**，再进 S6
- `S7 入口 B（解释回放）` 服务于**模式 3**：**只读、不改判定、不产生新结果、无后置**

## 1.1 Prompt 层

| 步骤 | 内容 | 完成判据 |
|---|---|---|
| 1.1.1 | 角色与边界：计算机专业实验报告评阅专家；定位为教师"副驾驶"（辅助而非替代） | 对超范围请求能明确拒绝 |
| 1.1.2 | 契约优先：输出必须是合规 ReviewResult JSON，结构先定 | 输出可被 schema 直接解析 |
| 1.1.3 | 口径硬写：总分公式 + 权重序列 + 档位系数，全部显式写出 | **由 T4 确定性计算器产出，且与 T5 的 `total.recompute` 复算值相等（不接受手算）** |
| 1.1.4 | 证据纪律：无证据不得高置信；证据须为原文引用 + 可定位 | 高置信评分点 100% 带证据 |
| 1.1.5 | 输出纪律：固定骨架、少自由度、禁止自由发挥与多余叙述 | 输出中无未定义字段、无冗余散文 |

## 1.2 Skills 层

共 **8 个技能 S0–S7**，彼此以固定链路协作（见 1.0 三模式总览）。

| 步骤 | 技能 | 内容 | 完成判据 |
|---|---|---|---|
| 1.2.1 | **S0 任务识别与路由** | 判断走哪类模式；缺件只问不代做 | 三类意图能正确分流，不猜、不代选 |
| 1.2.2 | **S1 Rubric 构建** | 标准结构化 + 一致性自查 | 权重和 = 100、档位互斥且可判定；只编码不赋值 |
| 1.2.3 | **S2 报告解析** | 结构切分 + 原文坐标（只读不改） | 每个结构单元带回链坐标；未解析 ≠ 缺失 |
| 1.2.4 | **S3 证据取证与逐点判定** | 证据四元组 + 疑点清单 | 无证据不得高置信；引用须经 T3 校验通过 |
| 1.2.5 | **S4 总分计算** | 纯算术、可复算 | 出部分分与 `W_r`；数字由 T4 产出 |
| 1.2.6 | **S5 结构装配与自检** | 六项校验 + 限定重试 | 校验通过方可交付；不得改写判断内容 |
| 1.2.7 | **S6 评语生成** | 逐句挂证据；两种输入来源输出结构一致 | 不出现重复句式；不生成涉诚信表述 |
| 1.2.8 | **S7 复核与解释** | 两入口：A 复核清单 / B 解释回放 | 只呈现事实、不表态；入口 B 只读、无后置 |

## 1.3 Tools 层

共 **6 个工具 T1–T6**，均为纯函数命令行脚本（仅 Python 标准库、无网络、无 AI 调用）。

| 步骤 | 工具 | 内容 | 完成判据 |
|---|---|---|---|
| 1.3.1 | **T1 文档解析器** | **docx / pdf / md / txt** 文本与结构提取 | 四类输入均可解析；**PDF 为保守文字层抽取，使用时须标注局限**；正文有内容却识别不到任何标题时，必须写入失败清单并降级状态，不得报成功 |
| 1.3.2 | **T2 客观核查器** | 章节完整性 / 代码 API / 统计特征 / 查重 | 自行从结构块复算统计并与解析结果交叉核对；**结构不可用时不得断言「缺失」**；跨端一致性（与 Web 端核查器输出一致）**待交付物二建立后校验** |
| 1.3.3 | **T3 引用解析器** | 按坐标还原逐字原文，并判定引用是否忠实 | 逐字比对**不做任何模糊归一化**；坐标失效或引用不符即该项证据作废 |
| 1.3.4 | **T4 确定性计算器** | 总分 / `W_r` / 上界 / 等级映射 / 复核排序键 | 全部数字由本工具产出，**不接受口算**；上界 = 已计入权重合计 |
| 1.3.5 | **T5 契约校验器** | **六项检查**：schema 结构 / 权重和 / 档位模型 / 证据与引用 / 总分复算 / 指纹复算 | 六项**可独立运行、可单独报错**；遇到 schema 不支持的关键字必须报错，禁止静默跳过 |
| 1.3.6 | **T6 资产库** | 四类资产（样板 / Rubric / 样例 / 金标准）的确定性检索与存取 | 「目录不存在」与「库为空」必须可区分：前者报环境未就绪，后者才报未命中 |

## 1.4 Workflow 层

| 步骤 | 内容 | 完成判据 |
|---|---|---|
| 1.4.1 | 五 Agent 编排规格：Parser → Evidence → Grader → Reviewer → Feedback | 每环的输入、输出、置信度、证据引用齐备 |
| 1.4.2 | 编排形态：单会话分步 + 多会话分环，两种均支持 | 两种形态都能跑通同一份报告 |
| 1.4.3 | 失败处理：任一环失败的回退与重试路径 | 失败不中断全流程，有明确状态标记 |

## 1.5 Evaluation 层

| 步骤 | 内容 | 完成判据 |
|---|---|---|
| 1.5.1 | 指标定义：总分 MAE / 逐项命中率 / 档位一致率 / 置信度校准 | 每个指标都可由原始数据复算 |
| 1.5.2 | 评测脚本：批量跑样例并出报告 | 一条命令出评测报告 |
| 1.5.3 | 回归门禁：新版本指标劣化即回退 | 门禁可自动判定通过/不通过 |

## 1.6 输出稳定性专项（对应"稳定产出合规 JSON"）

这是本路径的硬指标：不是"能产出"，而是"每次都产出合规 JSON"。

| 步骤 | 手段 | 作用 |
|---|---|---|
| M1 | JSON 骨架先行 | 先固定输出结构，再填内容，杜绝结构漂移 |
| M2 | 少自由度 | 评分点枚举、档位系数、总分公式全部固定，模型不自行发明 |
| M3 | 分步产出 | 解析 / 取证 / 评分 / 复核 / 评语分步生成，避免一次性长输出导致结构崩坏 |
| M4 | 自校验自修复回路 | 产出 → 校验 → 按错误清单重试（限定轮次），仍失败则标记待人工 |
| M5 | 异常输入兜底 | 空文件 / 超长 / 全截图 / 缺章节，均返回结构化失败而非崩溃 |
| M6 | 评测集回归 | 任何 Prompt 或 Skill 改动都过一遍样例集 + 对抗样本集 |

## 1.7 打包与平台合规映射

五件套不是终点。平台侧**不存在「开发者注册工具」通道**——官方明文：
「开发者不可自行添加 tools：所有工具权限由系统统一分配」。
从五件套到「平台能识别的专家包」还有一跳，缺了它整件事装不上。

| # | 平台硬约束 | 对应动作 |
|---|---|---|
| 1 | 工具权限由系统统一分配，开发者不可自行添加 tools | 确定性能力**只能做成可执行脚本**，由平台内置 `Bash` 调起，以绝对路径调用 |
| 2 | 插件根只认 `agents` / `skills` / `bin` / `avatars`；`tools/` **不是**平台认可落点 | 脚本映射到 `skills/<技能名>/scripts/`（首选）或插件根 `bin/` |
| 3 | 每个 Skill 必须是**含 `SKILL.md` 的目录** | 现有 8 份扁平规格须目录化为 `skills/<名称>/SKILL.md` |
| 4 | `agent.md` 的 frontmatter **禁写 `tools:` 字段**；`.codebuddy-plugin/plugin.json` 为必需 | 生成合规的 `plugin.json` 与 `agents/<agentName>.md` |
| 5 | 专家包落点固定：`$WORKBUDDY_CONFIG_DIR/plugins/marketplaces/my-experts/plugins/<专家名>/` | **不在该目录则无法被检测到** → 做成「复制到该目录 + 运行注册脚本」的一步 |
| 6 | 调用约定 | `python3` 优先、`python` 回退（随包运行时已含 python3） |

完成判据：在干净环境按 README 把专家包放到市场目录 → 运行注册脚本 → **专家中心可见** → 给它一份新报告能产出合规 JSON。

# 五、路径依赖关系

路径 0 是所有路径的根，未冻结则后续全部返工；路径一与路径二可部分并行，但共用 ReviewResult 契约，契约改动会同时影响两者；路径三最后做，因为它的内容是前两条路径的呈现。

路径 0 前置冻结 └─→ 路径一 专家智能体包 ├─→ 路径二 Web Demo（消费契约与评阅结果） └─→ 路径三 评审材料（消费智能体与产品形态）


# 六、明确排除（范围外）

不做时间规划、工期倒排与进度压力管理

不再考虑"备用链接"相关路径

不引入第三方模型依赖（openai / anthropic / langchain-* 等）

不做生产级后端、数据库、鉴权、多用户与成绩管理

# 七、一句话

先冻契约，再炼智能体，后搭界面，最后收证据。

顺序不能换：契约一动，智能体与界面同时返工；智能体不稳，界面就只能展示死数据。
