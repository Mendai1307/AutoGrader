# 高校计算机专业实验报告通用 Rubric

> 机器可读版本：[`rubric.json`](./rubric.json)（字段与 `frontend/lib/schema.ts` 的 `RubricSchema` / `RubricItemSchema` 严格对齐）
> 配套样例：[`../sample-reports/`](../sample-reports/)（12 份合成样例报告 + `manifest.json` 金标准分数）
> 版本：`1.0.0`（与 `rubric.json` 的 `version` 一致）

---

## 一、评分理念

本 Rubric 面向**高校计算机专业实验报告**（操作系统 / 计算机网络 / 数据结构与算法三个方向），服务于 AutoGrader 的五 Agent 流水线（Parser → Evidence → Grader → Reviewer → Feedback）。设计上遵循四条原则：

### 1. 证据先行，而不是印象打分

评分的每一步都必须能落到报告里的**具体证据**：一段正文（`text`）、一个代码块（`code`）、一张截图（`figure`）或一张数据表（`table`）。没有证据支撑的结论不得给分；证据不足时判低档并写明"未找到证据"，**严禁编造证据**。

### 2. 能力导向，重"做对"更重"想明白"

代码能跑通只是及格线。本 Rubric 把 **50% 的权重**压在"做出来"（核心代码正确性 20%、关键 API/算法使用 10%、实验步骤 7%、实验环境 5%、实验结果与截图 11% 中的产出部分），把 **30% 的权重**压在"想明白"（原理阐述 12%、数据分析与讨论 13%、问题排查与反思 7%，减去重叠计入部分），其余用于目的理解、代码规范、格式规范与原创性。

其中占比最高的两项是：

- **R5 核心代码正确性（20%）** —— 实验的硬指标；
- **R8 数据分析与讨论（13%）** —— 区分"抄了一遍代码"与"真的做了实验"的关键项。

### 3. 四档判定，档位系数固定

每个评分点统一为四档，档位得分系数固定为：

| 档位 | 标识 | 得分系数 | 含义 |
|---|---|---|---|
| 优秀 | `excellent` | **1.0** | 完整且超出基本要求，有个人见解 |
| 达标 | `meeting` | **0.8** | 满足基本要求，细节有瑕疵 |
| 部分达标 | `partial` | **0.5** | 有形但不完整，存在可指出的缺陷 |
| 未达标 | `notMet` | **0** | 缺失，或存在原则性错误 |

单项得分 = `round2(maxScore × scoreRatio)`。各评分点的 `maxScore` 是教师自定标度（5 / 10 / 15 / 20 不等），**标度大小不影响该项在总分中的占比**，占比只由 `weight` 决定。

### 4. 总分口径唯一

```
totalScore = round2( Σ ( score_i / maxScore_i × weight_i ) )
```

即**先归一化成得分率，再乘权重百分比**，结果落在 0–100。由于 `score_i = maxScore_i × ratio_i`，实际等价于 `Σ (ratio_i × weight_i)`。各评分点权重之和**恰好为 100**。这一口径与 `frontend/lib/schema.ts` 的 `computeWeightedTotal()` 完全一致，前端可用 `verifyTotalScore()` 复算校验。

## 二、评分点清单

权重合计 **100**，共 **12** 个评分点。

| id | 评分点 | 权重 | 满分 | 主要证据类型 | 考查什么 |
|---|---|---:|---:|---|---|
| R1 | 实验目的理解 | 5 | 5 | text | 是否知道这次实验要做什么 |
| R2 | 原理阐述 | 12 | 10 | text / code / figure | 概念是否准确、机制是否讲清 |
| R3 | 实验环境配置 | 5 | 5 | text / table / figure | 实验是否可复现 |
| R4 | 实验步骤完整性 | 7 | 10 | text / code / figure | 流程是否完整可操作 |
| R5 | **核心代码正确性** | **20** | 20 | code / text | 代码能否正确完成核心功能 |
| R6 | 关键 API / 算法使用 | 10 | 10 | code / text | 是否用对了关键机制 |
| R7 | 实验结果与截图 | 11 | 10 | figure / table / text | 是否有可辨识的原始结果 |
| R8 | **数据分析与讨论** | **13** | 15 | text / table / figure | 是否对数据做了量化归因 |
| R9 | 问题排查与反思 | 7 | 10 | text / code / figure | 是否真的踩过坑并解决 |
| R10 | 代码规范 | 5 | 10 | code | 代码是否可读、可维护 |
| R11 | 格式规范 | 3 | 10 | text / figure / table | 报告结构是否完整规范 |
| R12 | 原创性 | 2 | 5 | text / code | 是否独立完成、引用是否标注 |
| | **合计** | **100** | — | | |

> **说明**：证据类型以 `evidenceRequirement` 字段承载，格式固定为「证据类型：xxx。要求：……」，
> 类型取值与 `schema.ts` 的 `EvidenceKindSchema` 一致（`text` / `code` / `figure` / `table`）。
> 之所以内嵌在字符串而非新增字段，是因为 `RubricItemSchema` 使用了 Zod `.strict()`，
> 未知字段会被直接拒绝；这样可保证 `rubric.json` 能被 `RubricSchema.safeParse` 原样通过。

## 三、各评分点判定标准

以下为摘要，完整判定文案与扣分梯度见 `rubric.json`。

### R1 实验目的理解（5% / 满分 5）

- **优秀**：3 条以上具体目标，覆盖知识目标与能力目标，后文每个目标都有结果与结论回应。
- **达标**：2–3 条目标，表述基本清晰，个别目标缺少结果回应。
- **部分达标**：仅 1 条笼统目标（如"学习多线程编程"），或整段抄自指导书。
- **未达标**：无目的章节，或目的与实验主题无关。
- **扣分梯度**：目标条目达标但有 1 条与后文无对应 → 降一档；出现与主题无关的目标，每条再扣 0.5 分。

### R2 原理阐述（12% / 满分 10）

- **优秀**：概念定义准确完整，能说明机制"为什么成立"，并结合代码/数据结构具体说明，无科学性错误。
- **达标**：核心概念正确、覆盖主要机制，但停留在定义复述，与代码对应关系偏弱。
- **部分达标**：零散提及术语，存在概念混淆（进程/线程、互斥/同步、平均/最坏复杂度），篇幅不足。
- **未达标**：完全缺失，或存在原则性错误（如"信号量能解决一切死锁""TCP 天然保证消息边界"）。
- **扣分梯度**：每处科学性错误再扣 2 分，原则性错误直接判未达标；原理与实现脱节扣 3 分；整段照抄教材无个人归纳扣 1 分。

### R3 实验环境配置（5% / 满分 5）

- **优秀**：OS、语言/编译器版本、依赖库版本、编译与运行命令四要素齐全，他人可复现。
- **达标**：给出 OS 与主要工具版本，缺少个别次要信息。
- **部分达标**：只写工具名无版本号，或截图无法辨识版本。
- **未达标**：完全未交代环境。
- **扣分梯度**：缺版本号每处扣 1 分；缺编译/运行命令扣 1 分；版本与代码语法矛盾扣 2 分；仅截图且文字不可辨识降一档。

### R4 实验步骤完整性（7% / 满分 10）

- **优秀**：步骤编号完整，覆盖准备、实现、编译、运行、记录、导出六个环节，关键步骤有命令与参数。
- **达标**：主要环节齐全，个别环节无命令说明，缺结果导出环节。
- **部分达标**：仅粗略几步（"写代码→运行"），缺编译/参数/记录环节，或顺序混乱。
- **未达标**：无步骤章节，或步骤与内容无关。
- **扣分梯度**：缺失一个关键环节扣 2 分；编号缺失或顺序颠倒扣 1 分；命令与代码文件名不一致每处扣 1 分。

### R5 核心代码正确性（20% / 满分 20）

- **优秀**：核心功能完全正确，边界条件处理完备（空输入、单元素、连接异常、极端并发），无资源泄漏，有返回值检查与错误处理。
- **达标**：主要功能正确，常规输入结果正确，边界或异常处理有遗漏但不影响主流程。
- **部分达标**：存在可指出的明确缺陷（锁粒度错误、共享变量未保护、`recv` 返回值未处理导致粘包、比较逻辑有误），部分输入下结果错误。
- **未达标**：无核心代码块，或代码无法编译运行，或核心逻辑完全错误。
- **扣分梯度**：每处明确 bug 扣 3 分；资源泄漏每处额外扣 2 分；无法编译直接判未达标；只有运行结果无代码判未达标；核心机制与要求不符扣 5 分。

### R6 关键 API / 算法使用（10% / 满分 10）

- **优秀**：关键 API/算法选用恰当、调用惯用法正确、参数与返回值处理规范，并说明选型理由与替代方案对比。
- **达标**：使用了正确的 API/算法，调用基本规范，但未说明选型理由或个别参数不够地道。
- **部分达标**：用了要求的关键 API/算法但用法有误（条件变量配合错误、忘记 `setsockopt`、递归终止条件写错），或以简化实现回避关键 API。
- **未达标**：完全未使用要求的关键 API/算法（要求 socket 却用现成框架、要求实现快排却直接调库且不说明）。
- **扣分梯度**：关键参数错误每处扣 2 分；使用不安全接口（`strcpy`/`gets`）每处扣 2 分；使用库函数但明确说明并与自实现对比，不扣分。

### R7 实验结果与截图（11% / 满分 10）

- **优秀**：3 张以上截图/表格，覆盖主要实验场景，均有编号与图题，关键数据清晰可辨识，正文逐一引用并解读。
- **达标**：2 张左右截图，编号图题基本齐全，能支撑主要结论，个别场景缺失或数据不可辨识。
- **部分达标**：仅 1 张截图，或缺编号/图题，或截图与内容不匹配（只截代码编辑界面），不足以支撑结论。
- **未达标**：完全没有结果截图或结果数据。
- **扣分梯度**：无编号或图题每张扣 1 分；未被正文引用每张扣 1 分；伪造或无关截图判部分达标并扣 3 分；未用表格呈现对比数据扣 2 分。

### R8 数据分析与讨论（13% / 满分 15）

- **优秀**：多组量化数据对比与计算（加速比、增长率、相对误差），结合原理解释成因，指出与理论预期的偏差并给出可信解释，有个人见解。
- **达标**：有量化对比与基本解释，能说明主要趋势，但归因较浅或未与理论值对照。
- **部分达标**：只罗列现象无量化分析（"加了锁变慢了"却不给数值），或只有结论无数据支撑。
- **未达标**：完全没有数据分析与讨论，直接跳到总结。
- **扣分梯度**：图表数值与正文矛盾每处扣 3 分；仅重复描述截图内容降一档；仅 1 组数据即下结论扣 3 分；结论超出数据支持范围扣 2 分。

### R9 问题排查与反思（7% / 满分 10）

- **优秀**：记录 2 个以上具体问题，含现象、定位过程、根因与解决办法，并给出方案局限与至少 1 条可执行改进方向。
- **达标**：记录 1–2 个问题并给出解决办法，但排查过程简略或反思偏套话。
- **部分达标**：仅笼统提到"遇到了一些困难"而无具体问题与解决办法，或只有反思无问题记录。
- **未达标**：完全无问题排查与反思。
- **扣分梯度**：问题已提出但未给解决办法每个扣 2 分；解决办法与问题不匹配扣 3 分；反思空洞套话扣 2 分。

### R10 代码规范（5% / 满分 10）

- **优秀**：命名规范统一，缩进空行一致，关键逻辑有注释说明"为什么"，常量已提取命名，无调试残留，代码块带语言标注。
- **达标**：整体可读，命名缩进基本规范，但注释偏少或仅描述"做了什么"，有少量魔法数字或调试残留。
- **部分达标**：命名随意（`a`/`b`/`tmp1`）或缩进混乱，几乎无注释，代码块缺语言标注，有大段注释掉的代码。
- **未达标**：代码以截图给出无法复制，或未给出任何代码块。
- **扣分梯度**：无意义命名每处扣 0.5 分；调试残留每处扣 1 分；代码块缺语言标注每处扣 1 分；用图片代替代码文本直接降一档。

### R11 格式规范（3% / 满分 10）

- **优秀**：章节结构完整，标题层级清晰，图表编号连续且题注规范，引用标注规范，排版整洁。
- **达标**：结构基本完整，图表有编号，但个别章节缺失、编号不连续或文献格式不统一。
- **部分达标**：缺 2 个以上必要章节，或标题层级混乱、图表无编号、篇幅明显不足。
- **未达标**：结构严重缺失（只有代码没有正文），或全文无标题层级。
- **扣分梯度**：缺失一个必要章节扣 2 分；图表编号缺失或不连续每处扣 0.5 分；篇幅低于规定下限扣 2 分；残留其他实验的模板标题扣 2 分。

### R12 原创性（2% / 满分 5）

- **优秀**：参数与测试用例有个人设计痕迹，数据与代码一致，引用处均注明出处。
- **达标**：整体独立完成，个别片段参考公开资料但未注明，或参数完全照搬指导书默认值。
- **部分达标**：有明显照抄痕迹（代码风格与正文描述割裂、数据与他人雷同），未发现直接复制的整段内容。
- **未达标**：确认存在整段抄袭且无引用标注。
- **扣分梯度**：未标注引用的参考内容每段扣 1 分；数据明显伪造（违背基本规律）扣 2 分；确认抄袭判未达标并按课程学术规范另行处理。

## 四、使用方式

### 4.1 教师：如何套用

1. **直接沿用**：把 `rubric.json` 交给 AutoGrader，五 Agent 流水线会逐项抽取证据、判档、评分、复核并生成评语。
2. **按课程微调**：只改 `weight`（保证合计 100）与各项 `criterion` 文案，**不要改** `scoreRatio` 的四档语义，否则历史成绩不可比。
3. **按实验微调**：单个实验不需要全部 12 项时，把该项 `weight` 置为 `0`（schema 允许权重为 0，仅作诊断不给分），**不要删除评分点**，以免破坏结果文件的可复算性。
4. **升级版本**：修改后递增 `version`（`MAJOR.MINOR.PATCH`），与契约的 `schemaVersion` 相互独立。

### 4.2 AI 流水线：如何判档

1. **Parser** 切分章节树（目的 / 原理 / 环境 / 步骤 / 代码 / 结果 / 分析 / 总结）。
2. **Evidence** 按各项 `evidenceRequirement` 声明的证据类型抽取证据，**逐字摘录**不改写，并给出每条证据的置信度。
3. **Grader** 比对证据与四档 `criterion` 判档，`score = round2(maxScore × scoreRatio)`，按 `deductionNotes` 记录扣分理由。
4. **Reviewer** 对置信度 < 0.80、证据为空、或档位存在跨两级争议的项复核。
5. **Feedback** 依据档位分布生成个性化评语，亮点与建议都须落到具体证据。

**判档红线**：未找到证据时不得编造，应置 `notMet`、`score = 0`、`deductionReason` 写明"未找到证据"。

### 4.3 校验总分

```ts
import { validateReviewResult, verifyTotalScore } from '@/lib/schema';

const result = validateReviewResult(json);
if (result.ok) {
  const check = verifyTotalScore(result.data); // { expected, actual, delta, ok }
}
```

`demo/sample-reports/manifest.json` 中的 `goldTotalScore` 均按同一公式逐份手工核算，可作为 AI 评分一致性的回归基准。

## 五、评分点覆盖维度对照

| 建议覆盖维度 | 对应评分点 |
|---|---|
| 实验目的理解 | R1 |
| 原理阐述 | R2 |
| 实验环境配置 | R3 |
| 实验步骤完整性 | R4 |
| 核心代码正确性 | **R5** |
| 关键 API / 算法使用 | R6 |
| 实验结果与截图 | R7 |
| 数据分析与讨论 | **R8** |
| 问题排查与反思 | R9 |
| 代码规范 | R10 |
| 格式规范 | R11 |
| 原创性 | R12 |

两大核心维度定位：**代码正确性 = R5（20%）+ R6（10%）**，**实验分析 = R8（13%）+ R7（11%）+ R9（7%）**。
