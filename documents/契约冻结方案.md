## 2. 三处语义冲突（不是命名冲突，必须裁决）

> 命名冲突照 §3 的表机械对齐即可；**这三处必须做设计裁决**，否则冻结了也是错的。

### 冲突一｜`needsReview` ↔ `pending`：合并会打爆全部历史总分

| | v0.1 `needsReview` | 新设计 `pending` |
|---|---|---|
| 语义 | 「该项**需要教师看一眼**」（置信度 < 0.80、证据缺失、或档位有争议） | 「该项**尚无终值**，**不计入总分求和**」 |
| 对总分的影响 | **无**——`computeWeightedTotal` 对全部 `scores` 求和，不排除任何项 | **有**——T4 `compute_total` 明确排除 `pending` 项并计入 `W_r` |

**若直接改名会怎样（推演，可复算）**：12 份历史资产里凡 `needsReview: true` 的项会突然被排除出总分 → 每份的 `totalScore` 变化 → 前端 `verifyTotalScore`（容差 0.01）**全数失败** → 前端会把 12 份资产全部标为「**结果已被修改**」。同时路径 0.1 的完成判据「12 份既有结果全部通过 zod 校验」中隐含的一致性核查也一并失败。

**建议：两个字段并存，语义正交。**

```
needsReview  (保留，v0.1 语义不变)  = 该项需要教师看一眼
pending      (新增，optional，默认 false) = 该项尚无终值，不计入总分求和
```

不变式（写进契约说明）：

- `pending === true` ⟹ `needsReview === true`（待复核必然需要复核）
- 反之**不成立**（可以「需要复核」但已有终值——例如教师复核过后仍标留意）
- **T4 只认 `pending`**；**S7 入口 A 用 `needsReview` 排序**
- 历史资产无 `pending` → 缺省 false → 总分不变 → 全部继续通过

### 冲突二｜档位模型不可调和：`levels[]` vs `bands[]{from,to}`

| | v0.1 `RubricItem.levels[]` | T5 `check_bands` 期望的 `bands[]` |
|---|---|---|
| 形状 | `{ level: 4值枚举, label, criterion: 判据文本, scoreRatio: 0–1 }` | `{ from: number, to: number }` |
| 「档」是什么 | **语义等级 + 得分系数 + 可判定判据** | **数值区间** |
| 得分关系 | `score = maxScore × scoreRatio`（`verifyItemScore` 强制） | 无 |
| 键名 | `levels` | `bands` |

**后果（实测已证）**：`check_slots` 里 `it.get("bands")` 对真实 Rubric 恒为 `None` → 档位检查**静默跳过**。所以**即使修好 AUDIT P0-3 的死代码，对真实 Rubric 仍然什么都不查**——这是一个「修了 bug 也没用」的陷阱。

**建议：以 v0.1 的 `levels[]` 为准，改造 T5。废弃 `bands[]{from,to}`**（或降为可选扩展，仅供数值型评分点使用）。

T5 在 `kind === 'rubric'` 时应校验：

1. `levels[]` 非空
2. 同一 item 内 `level` **不重复**（互斥）
3. `scoreRatio` 随档位严格单调（`excellent > meeting > partial > notMet`）——**这是「档位不重叠」在系数模型下的正确表达**，取代区间重叠检测
4. `scoreRatio ∈ [0, 1]`（契约已保证，工具仍需独立复核）
5. `criterion` 非空
6. （建议但不必强制）四档齐全性——教师可能只要两档
7. **可判定性**：`criterion` 与 `label` 命中关键词黑名单（「较好 / 一般 / 较差 / 良好 / 态度认真 / 内容完整」等）→ 报 `band.vague-criterion`
   > 说明：严格的「可判定性」是语义判断，属 S1。T5 只做**关键词黑名单**这一确定性部分，并在输出里明确标注这是**线索**不是结论——符合 `tools/README` 的 Tool/Skill 分界判据。

### 冲突三｜`totalScore` 单一数值无法表达「部分分 + 上界」

| | v0.1 | 新设计 |
|---|---|---|
| 字段 | `totalScore: number`（`.min(0).max(100)`） | `total { value, weightExcluded, upperBound, isPartial, grade }` |
| 求和范围 | **全部** scores | **仅** `pending === false` 的项 |
| 等级 | **无此概念** | `grade`（仅 `W_r = 0` 且已计入权重和 = 100 时有值） |

**建议：字段保留 + 语义窄化 + 新增 optional 子对象。**

```
totalScore  number 0–100     // 语义窄化为「按已生效终值求和的部分分」
                             // 部分分必然 ≤ 100，故 .max(100) 无需改动
total?      {                // 新增 optional；历史资产无此键
  weightIncluded  number     // Σ已计入 weight
  weightExcluded  number     // W_r
  upperBound      number     // = Σ已计入 weight   ← 不是 100 − W_r，见 AUDIT P1-8
  isPartial       boolean    // weightExcluded > 0
  grade           ScoreLevel | null
}
```

**同时需修订 `computeWeightedTotal`**：排除 `pending === true` 的项。历史资产无 `pending` → 行为不变。

> ⚠️ **`upperBound` 的定义必须改**。`T4-deterministic-calculator.md`、`SYSTEM_PROMPT` §3.2 与 §7.2 现都写 `100 − W_r`，而实测在权重和 = 60 时该式返回 `100.0`（真实上限 60）。正确式为 **`Σ已计入 weight`**；`100 − W_r` 仅在权重和恰为 100 时等价。**这是 4 处文字 + 1 行代码的联动修改。**

```
} .strict()
  .superRefine( 权重和 ≈ 100（容差 0.01）                      [旧]
                同一 rubricItemId 不得重复                      [旧]
                内嵌 rubric.version === rubricVersion           [旧]
                内嵌 rubric 权重和 ≈ 100                        [旧]
                [新] pending 项必须同时 needsReview === true
                [新] overriddenByTeacher === true ⟹ suggestedScore 存在且 ≠ score
                [新] total.isPartial === (total.weightExcluded > 0)
                [新] total.grade 非 null ⟹ weightExcluded === 0 且 weightIncluded === 100
                [新] totalScore === round2(Σ 非 pending 项的 score/maxScore×weight)，容差 0.01 )
```

**关于 `.strict()` 与「[新] 字段」的兼容性说明**：
`.strict()` 拒绝**未知**字段。新增字段一旦写进 schema 就是**已知**字段，历史资产**不填**它 → optional → 通过。二者不冲突。**这是路线 A 成立的技术前提。**

## 5. 指纹算法：v0.1 已定义完整（路径 0.3 实为「移植」）

**这是本轮最重要的正面发现。**

`frontend/lib/schema.ts:371-376` 的 `resultFingerprint` docstring 已给出**算法 + 规范化规则**的完整定义：

> 结果指纹：形如 `"sha256:<64位十六进制>"`。
> **算法**：将本 `ReviewResult` 对象按**字典序递归排序键**、`provenance.resultFingerprint` **置为 `""`**，序列化为**无空格 UTF-8 JSON** 后取 **SHA-256 十六进制小写**。
> 前端可用 Web Crypto 复算，不一致即提示「结果已被修改」。

约束正则（`:377-379`）：`/^(sha256:)?[0-9a-f]{8,128}$/i`

**它已经覆盖了「只给算法不给规范化规则，第三方复算仍会不一致」这一缺口**——递归键序、自指字段置空、无空格、编码、大小写**全部写死**。

### 5.1 移植时必须补死三条（否则跨语言复算仍不等）

| # | 问题 | 必须的规定 |
|---|---|---|
| 1 | **浮点表示** | Python 的 `json.dumps` 与 JS 的 `JSON.stringify` 对同一 double 的输出**不保证逐字相同**（如 `97.2` vs `97.19999999999999`）。→ **契约规定：所有分数 / 权重 / 置信度落盘前 `round(x, 2)`，且序列化时按最多 2 位小数输出** |
| 2 | **`null` vs 缺失键** | JS 的 `JSON.stringify` 丢弃 `undefined` 但保留 `null`；Python 无 `undefined`。→ **契约规定：「字段不存在」= 不出现该键；「无值」= 显式 `null`。两者不可混用**（v0.1 已用 `deductionReason: string\|null`、`scoreBefore: number\|null` 实践此约定，需显式写死） |
| 3 | **键序遍历顺序** | JS 对象在 `JSON.stringify` 中会把整数样式的键前置。→ **契约规定：两侧都做递归排序，不得依赖语言默认序** |

### 5.2 交付物

一个 T5 可加载的模块：

```python
# fingerprint.py   用法：--fingerprint-algo <path>
def fingerprint(obj) -> str:      # 返回 "sha256:<64位小写十六进制>"
    ...
```

## 6. T5 的 Schema 校验能力缺口（冻结时必须一并决定）

### 6.1 缺口

v0.1 契约的**最强防幻觉机制**是「全对象 `.strict()`」——`schema.ts:13` 注释原文：「全部对象使用 `.strict()`：**未知字段一律拒绝，防止 AI 自由发挥导致资产腐化**」。

但 T5 的 `validate_schema`（`contract_validator.py:59-93`）只支持：

```
type / enum / minimum / maximum / required / properties / items / minItems
```

**不支持**：`additionalProperties` / `pattern` / `minLength` / `oneOf` / `anyOf` / `const` / `$ref`。

→ **即使契约冻结，`.strict()`、正则约束字段（如 `resultFingerprint` 的格式校验）、union 类型都无法表达。**

### 6.2 三条路线

| 路线 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | **扩展 T5 的 Schema 子集**：补 `additionalProperties:false`、`pattern`、`minLength`、`const`、`oneOf`（`$ref` 用冻结时**内联展开**规避） | 保持「契约是唯一真源、跨端共用」的目标；改动集中在 1 个函数 |
| B | 放弃 JSON Schema 中介，用 Python 直写契约校验器 | 更可控，但破坏「同一份契约同时约束智能体 / 前端 / 仓库数据」的三方一致性叙事——而这正是本项目的**技术创新性卖点** |
| C | 引入第三方 `jsonschema` 包 | ❌ **违反**「仅标准库、无第三方依赖」硬约束，排除 |

### 6.3 无论选哪条，都必须加一条硬约束

> **`validate_schema` 遇到不认识的关键字时，必须 `exit 2` + 结构化报错，禁止静默跳过。**

理由：当前实现（`:56` 的 `if not isinstance(schema, dict): return`）对未知关键字**完全不处理**——这正是 AUDIT P1-7「静默放行」的同一类病根。一份「以为自己校验了、其实没校验」的 schema 比没有 schema 更危险。

## 8. 权重序列与总分口径（已冻结，但有 4 处文字 + 1 行代码要改）

**已冻结、不得改写**（本方案不动）：

```
总分 = Σ (score / maxScore) × weight          —— 不是 Σ (score × weight / 100)
权重序列（和 = 100）：5 / 12 / 5 / 7 / 20 / 10 / 11 / 13 / 7 / 5 / 3 / 2
待复核项不计入求和，不做归一化；总分是部分分（下界），须携带 W_r
等级仅在 W_r = 0 且已计入权重合计 = 100 时映射
```

**v0.1 的 `computeWeightedTotal` 与上述口径完全一致**（`schema.ts:556-562`，含 `round2`）——这是一条**独立于文本的代码级佐证**，说明口径在 v0.1 就已正确落地。

## 9. 迁移与不变性验证

### 9.1 目标

**12 份历史资产一行不改，继续通过校验。**

### 9.2 手段

1. 本轮所有新增字段**一律 optional**
2. `pending` 缺省 `false`、`overriddenByTeacher` 缺省 `false`
3. `total` 子对象 optional
4. `taskType` 等新增顶层字段 optional

### 9.3 ⚠️ 明确不做：**不得自动回填 `suggestedScore`**

历史资产的 `score` 是「AI 直接给的分」，当时**没有终值概念**。若把 `score` 复制成 `suggestedScore` 并置 `overriddenByTeacher: false`，等于**伪造了一条「AI 建议 = 终值」的评测数据** → 直接污染 Evaluation 层的总分 MAE 与逐项命中率（v0.1 的 MAE 3.05 就是这么算出来的，回填会让它变成「自己跟自己比」，恒等于 0 误差）。

**正确做法**：
- 用 `schemaVersion` 区分：历史 = `'1.0.0'`，新产出 = `'1.1.0'`
- Evaluation 脚本**显式排除 `1.0.0` 资产**，或把历史 `score` 视为「来源不明的终值」并单列
- 差异数据（MAE / 命中率）**只对 `1.1.0` 资产计算**

### 9.4 可以自动做的（纯推导，不引入新信息）

回填历史资产的 `total` 子对象：由现有 `totalScore` 与 `scores[].weight` **纯推导**可得
`weightIncluded = 100`、`weightExcluded = 0`、`upperBound = 100`、`isPartial = false`、`grade = ` 按 `totalScore` 映射。
→ **建议做**，让前端对新旧资产同构渲染，无需分叉逻辑。

### 9.5 版本号

`SCHEMA_VERSION` `'1.0.0'` → `'1.1.0'`（新增 optional 字段 = **MINOR**，符合语义化版本约定）。
`provenance.schemaVersion` 与顶层 `schemaVersion` **须同时更新且一致**——v0.1 的 superRefine 已含此约束，勿绕过。
