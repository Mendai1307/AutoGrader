## 一、赛事硬约束提取

来源：`docs/deliverable-strategy.md` 第一节「约束提取与架构含义」（该表原文出自赛事答疑聊天记录）、
`docs/learnbuddy-usage.md` 第一节「先理解规则，再谈功能」，并经 `MEMORY.md` 固化为长期决策。

| # | 约束（原文口径） | 架构含义 |
|---|---|---|
| 1 | 以 LearnBuddy 平台为载体，最终呈现**最好不要包含第三方 AI** | 禁止引入 OpenAI / Anthropic / DeepSeek 等 API；仓库不留相关 SDK 依赖 |
| 2 | 平台**没有开放给网页用的 API** | Web 前端无法在运行时调用 LearnBuddy，不存在「前端调 AI」这条路 |
| 3 | 初赛**提交 demo 即可，不用部署正式环境** | 不需要生产级后端、数据库、鉴权、监控 |
| 4 | 作品须**部署至浏览器环境，提供可直接访问的在线链接** | 必须有 URL；纯静态站点是最稳的达标方式 |
| 5 | 须提交**完整源代码仓库** | 代码要能 clone 下来跑通，依赖越少越好 |
| 6 | 需提交 **LearnBuddy 历史对话记录**作为评审参考 | 对话记录 = AI 能力的唯一合法证明，必须「厚」且「可追溯」 |
| 7 | 赛前壳子**不可复用**，要比赛开始后的对话记录 | 产物必须在赛程内由对话产生 |
| 8 | 智能体可以是 **web demo，也可以是专家智能体** | 两条路都合规 → 采取「两条都走」的双形态策略 |

补充风险提示（同源）：**「赛前做的壳子和设计计划不可以复用」**。
`docs/learnbuddy-usage.md` 保留了当时的赛前快照，并已标注**该快照已过期**——当前仓库不含任何 0 字节占位文件。

> 关于约束 7 的核实：`2026-09-21.md` 记载「比赛正式开始时间」已确认为**比赛进行中**，因此无需顾虑骨架重生问题。

## 二、三个核心矛盾

来源：`docs/deliverable-strategy.md` 第二节。

- **矛盾 A · 实时评分 vs 第三方 AI**：想要「用户上传报告 → 实时出评分」，但这需要 LLM API，与约束 1、2 直接冲突。自己接 = 第三方 AI；调 LearnBuddy = 没有 API。
- **矛盾 B · 完整后端 vs 初赛形态**：想要 FastAPI + PostgreSQL 的完整后端，但约束 3 说不用正式环境。后端冷启动、数据库连接、鉴权都是稳定性与时间成本，且不产生评审加分。
- **矛盾 C · 投入方向错位**：评审看的是对话记录，不是运行时的你。做「真实可用后端」评委看不到；做「对话记录」评委一定会看。

## 三、范式切换论证：从 Runtime AI 到 Compile-time AI

来源：`docs/deliverable-strategy.md` 第三节；`MEMORY.md` 已将其固化为**长期决策第 2 条**。

```
【原设想 Runtime AI】
用户上传 → 浏览器 → FastAPI → LangGraph → 第三方 LLM → 数据库 → 返回
                              ↑ 违规：第三方 AI

【修订后 Compile-time AI】
开发时：LearnBuddy 对话中上传报告 → 五 Agent 流水线推理 → 产出评阅 JSON → 提交进仓库
运行时：浏览器 → 读仓库内 JSON → 确定性渲染 + 浏览器端规则核查 → 展示
                  ↑ 零 AI 调用，零后端
```

切换带来的三个附加收益（原文口径）：

1. **结果可复现**：评阅结果固化成 JSON，评委每次打开链接看到同一份结果，不会因模型随机性翻车；
2. **可审计**：每份 JSON 都能对应到某一次 LearnBuddy 对话，形成证据链；
3. **可评测**：因为有金标准 JSON，可以做一个「AI vs 教师一致性」评测页 —— 这是评委最吃的硬证据。

该范式是纯静态架构的前提，也是能同时吃下多个静态托管平台的原因。

## 四、技术栈修订决策

来源：`docs/deliverable-strategy.md` 第五节「技术栈逐项修订」；结论同步写入 `MEMORY.md`。

| 原设想 | 修订决策 | 理由 |
|---|---|---|
| Next.js + React + TS | ✅ 保留，改为 `output: 'export'` 静态导出 | 去掉 SSR / Server Action 依赖，产物可直接静态托管 |
| Tailwind + shadcn/ui | ✅ 保留 | 展示层核心，AI 生成质量最高、最易出效果 |
| FastAPI 后端 | ❌ 初赛移除，降级为「离线批处理脚本」（不部署） | 约束 3 + 矛盾 B |
| LangGraph / 自定义 Agent Workflow | 🔄 改为「LearnBuddy Skill + 多 Agent 对话编排」，前端用 TS 状态机**可视化**该流程 | 真正的执行者是 LearnBuddy，不是 Python 进程 |
| PyMuPDF + python-docx | 🔄 改为 ① LearnBuddy 原生多模态解析（主）② 浏览器端 `pdf.js` + `mammoth.js`（辅） | 服务端没有 Python 运行环境 |
| PostgreSQL | ❌ 改为静态 JSON 数据层 + Zod schema | 无持久化、无多用户、无写入需求，「JSON 即数据库」 |
| Supabase Storage / S3 | ❌ 改为 `frontend/public/samples/` 静态资源 | 零外部依赖、零密钥 |
| Vercel | ✅ 保留（静态托管），备用 LearnBuddy 内置静态部署 | 两条路都能拿到可访问 URL |
| Render / Railway | ❌ 初赛移除 | 冷启动慢、配置成本高，且不需要跑后端 |

**建议新增的三项（低成本、高评分）**，本次均已落地为仓库产物：

1. 一致性评测页 `/eval` —— AI vs 教师金标准对比看板（`frontend/app/eval/`、`frontend/lib/analysis.ts`）；
2. 工作流溯源页 `/trace` —— 五 Agent 中间产物可视化（`frontend/app/trace/`）；
3. 浏览器端确定性核查器 `lib/inspectors/` —— 章节完整性、代码 API 命中、统计特征、SimHash 查重（纯前端、非 AI）。

## 五、双形态交付与耦合点

来源：`docs/deliverable-strategy.md` 第四节；`MEMORY.md` 长期决策第 3 条。

- **形态 A · 能力本体**：LearnBuddy「实验报告评阅专家」智能体（专家分身）—— 符合官方认可的「专家智能体」形态，产出对话记录（评审主证据）。
- **形态 B · 产品形态**：纯静态 Next.js Web Demo —— 符合「部署至浏览器环境 + 可访问链接」，产出在线 URL 与源码仓库。
- **耦合点**：Zod schema 定义的 `ReviewResult` 契约（`frontend/lib/schema.ts` + `docs/contract.md`），
  同时约束 LearnBuddy 的输出格式、前端类型定义与仓库内 JSON 资产三者。

> 如实标注（据 `2026-09-20.md` 与 `MEMORY.md` 的待办）：形态 A（专家智能体包）**尚未构建**；
> 本轮（2026-09-21）的归档与数据修复工作属于形态 B 侧的资产治理，不改变这一状态。
