AutoGrader · 交付形态与技术栈决策看板

AI Coding 创新大赛 · 高校教与学场景 · 创意验证阶段
核心结论：赛事规则与你的技术设想之间存在结构性冲突。你设想的是「实时 AI Web 应用」，但规则只允许「AI 推理在 LearnBuddy 侧、Web 端确定性呈现」的混合形态。建议采用双形态交付：LearnBuddy 专家智能体（能力本体）+ 纯静态 Next.js Demo（产品形态），用一份评阅结果 JSON 契约耦合。

一、规则约束提取

来自赛事答疑记录，每条都直接决定架构走向
约束 1 · 载体
以 LearnBuddy 为载体，最终效果呈现最好不要包含第三方 AI
约束 2 · 接口
平台没有开放给网页用的 API，前端无法运行时调 AI
约束 3 · 环境
初赛提交 demo 即可，不用部署到正式环境
约束 4 · 交付
须部署至浏览器环境，提供可直接访问的在线链接
约束 5 · 代码
须提交完整源代码仓库（GitHub / Gitee）
约束 6 · 证据
须提交 LearnBuddy 历史对话记录作为评审参考
约束 7 · 时效
赛前壳子不可复用，要比赛开始后的对话记录
约束 8 · 形态
智能体可以是 web demo，也可以是专家智能体

二、范式切换：Runtime AI → Compile-time AI

把 AI 推理从「用户打开网页的那一刻」前移到「开发时在 LearnBuddy 对话中」
原设想 · Runtime AI（违规）
用户上传→ 浏览器→ FastAPI→ LangGraph→ 第三方 LLM→ PostgreSQL→ 返回
红色删除线部分同时违反约束 1（第三方 AI）、约束 2（无 API）、约束 3（无需正式环境）
修订后 · Compile-time AI（推荐）
开发时：LearnBuddy 对话上传报告→ 五 Agent 流水线推理→ 产出评阅 JSON→ 提交进仓库
运行时：浏览器→ 读仓库内 JSON→ 确定性渲染 + 前端规则核查→ 展示
运行时零 AI 调用、零后端。附带收益：结果可复现、可审计、可做一致性评测

三、双形态交付

约束 8 明确两条路都合规，那就两条都走，互为佐证
形态 A · 能力本体
LearnBuddy「实验报告评阅专家」
· 用专家分身能力构建，注入评分方法论
· 师生可直接对话，上传报告获得真实评阅
· 产出：对话记录（评审主证据）
形态 B · 产品形态
纯静态 Next.js Web Demo
· 完整体验：上传→解析→逐项核查→复核→评语
· 数据来源：形态 A 生成的评阅 JSON 资产
· 产出：在线 URL + 源码仓库
耦合点 = 一份 Zod schema 定义的 ReviewResult 契约，同时约束：LearnBuddy 输出格式、前端类型、仓库 JSON 资产。

四、技术栈逐项修订

保留 3 项 · 改造 3 项 · 移除 4 项 · 新增 3 项
原设想结论修订理由
Next.js + React + TS保留改为 output: 'export' 静态导出去掉 SSR / Server Action 依赖，产物可直接静态托管
Tailwind + shadcn/ui保留不变展示层核心，AI 生成质量最高、最易出效果
Vercel保留静态托管；备用内置静态部署一键拿链接
（赛后补注：入口可达，但为 SPA 回退式托管、无目录索引 —— 深链与刷新回退首页，且链接生命周期不受本项目控制，故不可替代主链接）		两条路都能拿到可访问 URL
FastAPI移除降级为离线批处理脚本（可选，不部署）初赛无需正式环境；避免第三方 AI 嫌疑
PostgreSQL移除静态 JSON 数据层 + Zod schema无持久化、无多用户、无写入需求，JSON 即数据库
Supabase Storage / S3移除frontend/public/samples/ 静态资源样例随仓库分发，零外部依赖、零密钥
Render / Railway移除不需要无后端可跑，冷启动慢、配置成本高
LangGraph / Agent Workflow改造LearnBuddy Skill + 多 Agent 对话编排；前端用 TS 状态机可视化Workflow 的执行者是 LearnBuddy，不是 Python 进程
PyMuPDF + python-docx改造① LearnBuddy 原生多模态解析（主）
② 浏览器端 pdf.js + mammoth.js（辅）		服务端无 Python 运行时；前端解析让"上传新报告"有真实反应
backend/agents/*.py改造改为 *.md prompt 规格 / Skill保留 .py 会让评委误以为后端调了模型，增加违规嫌疑
—新增/eval 一致性评测页AI vs 教师金标准：逐项命中率、MAE、Kappa。回应"AI 评阅可不可信"，最高性价比的一页
—新增/trace 工作流溯源页展示章节树、证据原文、复核意见与置信度变化，回应"AI 是不是黑箱"
—新增lib/inspectors/ 浏览器端确定性核查器章节完整性、指定 API 调用检测、字数/截图统计、SimHash 查重——非 AI 但真实运行，补上静态 Demo 的真实感

五、风险与对策

高 · 对话记录太薄
一份报告一个对话，每个 Agent 单独成对话，迭代过程保留不删
高 · 被质疑"假 AI"
页面标注生成时间、来源智能体、结果指纹；提供 JSON 下载；README 附对话记录索引
高 · 残留第三方 AI 依赖
依赖白名单检查：禁止 openai / anthropic / langchain-* 进入依赖清单
中 · 赛前骨架复用
赛前快照（已过期）：当时仓库除 README 外全为 0 字节空文件，风险低。当前仓库已无任何 0 字节占位文件，全部为赛程内由对话生成的实写内容
中 · 样例隐私
全部使用合成 / 脱敏数据，README 声明数据来源
低 · 首屏加载慢
单份 PDF 控制在 3MB 内，报告原件懒加载

六、下一步（按优先级）

  1. 确认比赛正式开始时间 — 决定现有骨架是否需要整体重生成
  2. 锁定 ReviewResult 契约（Zod schema）— 后续所有工作的枢纽，先做这个
  3. 设计 Rubric 模板（8–12 个评分点）— 与专家分身多轮打磨
  4. 构建 10–20 份脱敏样例 + 金标准 — 一致性评测的基准
  5. 构建「评阅专家」专家分身 — 形态 A 落地
  6. 开发前端四页 — 形态 B 落地
  7. 部署 + 推仓库 + 写 README — 交付
决赛演进路径：初赛保持轻量；若晋级需要真实部署，再按需加回 FastAPI（编排层）、PostgreSQL、Supabase Storage，LangGraph 只做流程编排、模型能力仍走平台。
