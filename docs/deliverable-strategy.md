# 交付形态分析与技术栈修订建议

> 任务二交付物｜针对"最终交付产品到底是什么形态"的疑惑
> 核心结论：**你现在设想的是"实时 AI Web 应用"，但赛事规则只允许你交"AI 在 LearnBuddy 侧、Web 端确定性呈现"的混合形态。**
> 这不是妥协，而是本赛题唯一能同时满足"以平台为载体"和"可访问在线链接"的解。

---

## 一、约束提取与架构含义

| # | 规则原文（聊天记录） | 架构含义 |
|---|---|---|
| 1 | 以 LearnBuddy 平台为载体，**最好不要包含第三方 AI** | 禁止引入 OpenAI/Anthropic/DeepSeek 等 API；仓库里也不要留相关 SDK 依赖 |
| 2 | 平台**没有开放给网页用的 API** | Web 前端无法在运行时调用 LearnBuddy，不存在"前端调 AI"这条路 |
| 3 | 初赛**提交 demo 即可，不用部署到正式环境** | 不需要生产级后端、数据库、鉴权、监控 |
| 4 | 作品须**部署至浏览器环境，提供可直接访问的在线链接** | 必须有 URL；纯静态站点是最稳的达标方式 |
| 5 | 须提交**完整源代码仓库** | 代码要能 clone 下来跑通，依赖越少越好 |
| 6 | 需提交 **LearnBuddy 历史对话记录**作为评审参考 | 对话记录 = AI 能力的唯一合法证明，必须"厚"且"可追溯" |
| 7 | 赛前壳子**不可复用**，要赛后的对话记录 | 骨架必须在赛程内由对话产生（当前仓库除 README 外全为 0 字节空文件，风险低但需重生成 README） |
| 8 | 智能体可以是 **web demo，也可以是专家智能体** | 两条路都合规 —— 那就**两条都走**，互为佐证 |

## 二、你现在的三个核心矛盾

**矛盾 A：想要"用户上传报告 → 实时出评分"，但这需要 LLM API，与约束 1、2 直接冲突。**
任何在浏览器里实时出语义评分的方案，背后必然是某个大模型。自己接 = 第三方 AI；调 LearnBuddy = 没有 API。

**矛盾 B：想要 FastAPI + PostgreSQL 的完整后端，但约束 3 说不用正式环境。**
初赛评委打开一个链接看几分钟。后端冷启动、数据库连接、鉴权全是稳定性和时间成本，且不产生任何评审加分。

**矛盾 C：评审看的是对话记录，不是运行时的你。**
你花大力气做的"真实可用后端"，评委看不到；你花力气做的"对话记录"，评委一定会看。投入方向要对齐评分标准。

## 三、范式切换：从 Runtime AI 到 Compile-time AI

把 AI 推理**从运行时前移到开发时**：

```
【原设想 Runtime AI】
用户上传 → 浏览器 → FastAPI → LangGraph → 第三方 LLM → 数据库 → 返回
                              ↑ 违规：第三方 AI

【修订后 Compile-time AI】
开发时：LearnBuddy 对话中上传报告 → 五 Agent 流水线推理 → 产出评阅 JSON → 提交进仓库
运行时：浏览器 → 读仓库内 JSON → 确定性渲染 + 浏览器端规则核查 → 展示
                  ↑ 零 AI 调用，零后端
```

这个切换带来三个额外好处：
1. **结果可复现**：评阅结果固化成 JSON，评委每次打开链接看到同一份结果，不会因为模型随机性翻车
2. **可审计**：每份 JSON 都能对应到某一次 LearnBuddy 对话，形成证据链
3. **可评测**：因为有金标准 JSON，可以做一个"AI vs 教师一致性"评测页 —— 这是评委最吃的硬证据

## 四、推荐交付形态：双形态耦合

### 形态 A · 能力本体 —— LearnBuddy「实验报告评阅专家」智能体
- 用**专家分身**能力构建，注入评分方法论、Rubric 模板、样例库
- 教师/学生可以**直接与它对话**，上传报告获得真实评阅
- 符合官方"也可以是专家智能体"的认可形态
- 产出：对话记录（评审主证据）

### 形态 B · 产品形态 —— 纯静态 Next.js Web Demo
- 完整呈现产品体验：上传 → 解析 → 逐项核查 → 复核 → 评语 → 成绩单
- 数据来源：形态 A 在赛程内生成的评阅 JSON 资产（随仓库提交）
- 符合"部署至浏览器环境 + 可访问链接"
- 产出：在线 URL + 源码仓库

### 耦合点：评阅结果契约（这是整个方案的枢纽）
一份 Zod schema 定义的 `ReviewResult`，同时约束三件事：
- LearnBuddy 的输出格式（写在 prompt 里让它按此输出）
- 前端的类型定义（`frontend/lib/schema.ts`）
- 仓库里的 JSON 资产（`frontend/public/results/*.json`）

## 五、技术栈逐项修订

| 原设想 | 修订建议 | 理由 |
|---|---|---|
| **Next.js + React + TS** | ✅ 保留，改为 `output: 'export'` 静态导出 | 去掉 SSR/Server Action 依赖，构建产物可直接静态托管，也可本地 `npx serve` 预览 |
| **Tailwind + shadcn/ui** | ✅ 保留 | 展示层核心，也是 AI 生成质量最高、最易出效果的部分 |
| **FastAPI 后端** | ❌ 初赛移除<br>降级为"离线批处理脚本"（可选，不部署） | 约束 3 + 矛盾 B。若确实需要 Python 做文档预处理，做成一次性脚本，产出 JSON 后提交进仓库 |
| **LangGraph / 自定义 Agent Workflow** | 🔄 改为「LearnBuddy Skill + 多 Agent 对话编排」<br>前端用 TS 状态机**可视化**该流程 | Workflow 的真正执行者是 LearnBuddy，不是 Python 进程。前端只做"流程可视化 + 溯源展示" |
| **PyMuPDF + python-docx** | 🔄 改为两条替代路径<br>① LearnBuddy 原生多模态解析（主）<br>② 浏览器端 `pdf.js` + `mammoth.js`（辅，纯前端） | 服务端没有 Python 运行环境；浏览器端解析能让"上传新报告"有真实反应 |
| **PostgreSQL** | ❌ 改为静态 JSON 数据层 + Zod schema | 无持久化、无多用户、无写入需求。JSON 即数据库 |
| **Supabase Storage / S3** | ❌ 改为 `frontend/public/samples/` 静态资源 | 样例报告随仓库分发，零外部依赖、零密钥 |
| **Vercel** | ✅ 保留（静态托管）<br>备用：LearnBuddy 内置静态部署，一键拿链接 | 两条路都能拿到可访问 URL，内置部署更快且无需配置 |
| **Render / Railway** | ❌ 初赛移除 | 冷启动慢、配置成本高，且不需要跑后端 |

### 建议新增的三项（低成本、高评分）

**1. 一致性评测页 `/eval`**
教师金标准 vs AI 评分的对比看板：逐项命中率、总分 MAE、Cohen's Kappa、置信度校准曲线。
→ 直接回应"AI 评阅可不可信"这个评委必问的问题。这是**最高性价比的一页**。

**2. 工作流溯源页 `/trace`**
把五 Agent 流水线的中间产物全部可视化：解析出的章节树、每个评分点命中的证据原文、Reviewer 的复核意见与置信度变化。
→ 回应"AI 是不是黑箱"，展示"可解释的评阅"。

**3. 浏览器端确定性核查器 `lib/inspectors/`**
这部分**不是 AI，但真实运行**，能显著提升 Demo 真实感：
- 章节完整性：正则匹配"实验目的/环境/步骤/结果/总结"
- 代码核查：检测是否调用了指定 API（如 `fork` / `pthread_create` / `socket`）
- 统计特征：字数、代码块数、截图/图表数量、图表是否有引用说明
- 相似度：SimHash  shingles 本地比对（查重，纯前端可做）

→ 用户上传一份**新**报告时，页面能立刻给出真实的客观核查结果；语义判断部分标注"由 LearnBuddy 评阅专家生成"，并引导去形态 A 体验。这就把"静态 Demo"和"真实可用"的裂缝补上了。

## 六、修订后的目录结构

```
AutoGrader/
├── frontend/                       # 唯一部署单元（Next.js 静态导出）
│   ├── app/
│   │   ├── page.tsx                # 产品首页：价值主张 + 双形态入口
│   │   ├── grade/page.tsx          # 评阅工作台（核心交互）
│   │   ├── report/[id]/page.tsx    # 单份报告：逐项核查明细
│   │   ├── eval/page.tsx           # 【新增】AI vs 金标准 一致性评测
│   │   └── trace/page.tsx          # 【新增】五 Agent 工作流溯源
│   ├── components/                 # shadcn/ui + 业务组件
│   ├── lib/
│   │   ├── schema.ts               # 【核心】Zod：ReviewResult 契约
│   │   ├── inspectors/             # 【新增】浏览器端确定性核查器
│   │   └── workflow.ts             # 五 Agent 状态机（可视化用）
│   └── public/
│       ├── samples/                # 脱敏样例报告
│       └── results/                # LearnBuddy 生成的评阅结果 JSON
├── backend/                        # 降级：离线评阅工作台（不部署）
│   ├── agents/*.md                 # ← 由 .py 改为 prompt 规格 / Skill
│   ├── prompts/
│   └── tools/                      # 可选：本地批处理脚本
├── demo/sample-reports/
├── docs/
│   ├── learnbuddy-usage.md         # 任务一：能力×流程
│   └── deliverable-strategy.md     # 任务二：本文档
└── .learnbuddy/memory/             # 项目记忆（平台侧 AI 资产）
```

**关键动作**：`backend/agents/` 下现有的 5 个空 `.py` 文件，建议**改为 `.md`**。
原因：这五个 Agent 的执行者是 LearnBuddy（通过 prompt / Skill），不是 Python 进程。
保留 `.py` 会让评委误以为你在后端调用了模型，反而增加"第三方 AI"的嫌疑。

## 七、决赛演进路径（现在砍掉的不是永久砍掉）

若晋级决赛、要求真实部署，按需把下面几层加回来：

1. **后端**：FastAPI 重新引入，作为 Rubric 管理与批量任务编排层
2. **数据库**：PostgreSQL 存课程/班级/学生/成绩，Supabase Storage 存报告原件
3. **Agent 编排**：LangGraph 作为"任务编排"层（注意：仍然只编排流程，模型能力走平台）
4. **实时性**：若届时平台开放了可用接口，直接把形态 A 的专家智能体接进 Web

初赛阶段保持轻量，决赛再演进 —— 架构演进本身也是答辩时可以讲的"工程判断力"。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 对话记录太薄，无法证明 AI 能力 | 高 | 一份报告一个对话；每个 Agent 单独成对话；迭代过程保留，不删历史 |
| 被质疑"静态 Demo 是假的 AI" | 高 | 页面明确标注生成时间、来源智能体、结果指纹；提供完整 JSON 下载；README 附对话记录索引 |
| 仓库里残留第三方 AI 依赖 | 高 | 依赖白名单检查：禁止 `openai` / `anthropic` / `langchain-*` 等进入 package.json 与 requirements.txt |
| 赛前骨架复用争议 | 中 | 赛程开始后用对话重新生成 README 与全部代码（当前空占位文件本身无实质内容，风险可控） |
| 样例报告涉及真实学生隐私 | 中 | 全部使用合成/脱敏数据，README 声明数据来源 |
| 静态站点首次打开慢 | 低 | 报告原件放 public，控制单份 PDF < 3MB；懒加载 |

## 九、下一步建议（按优先级）

1. **确认比赛正式开始时间** —— 决定现有骨架是否需要整体重生成
2. **锁定 ReviewResult 契约**（Zod schema）—— 后续所有工作的枢纽，先做这个
3. **设计 Rubric 模板**（8–12 个评分点）—— 与专家分身多轮打磨
4. **构建 10–20 份脱敏样例 + 金标准** —— 一致性评测的基准
5. **构建「评阅专家」专家分身** —— 形态 A 落地
6. **开发前端四页** —— 形态 B 落地
7. **部署 + 推仓库 + 写 README** —— 交付

---

## 十、一句话结论

> **把 AI 放在 LearnBuddy 里跑，把产品放在浏览器里展示，把证据放在仓库和对话记录里。**
> 你要交付的不是"一个能调大模型的网站"，而是"一个由 LearnBuddy 专家智能体真实驱动的评阅系统，以及它的产品化界面与完整证据链"。
