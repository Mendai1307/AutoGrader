## 三、本轮修复（2026-09-21 · 归档与数据修复）

据 `2026-09-21.md` 的 5 天倒排规划，**D2（9-22）**的任务为：

本轮完成的是其中的**数据与归档部分**，不含重建（另行由集成工程师统一构建）。

### 3.1 对话记录归档（对应简报 P1「对话记录位于外部仓库、溯源语义弱」）

- 新增 `conversations/` 目录，含 `README.md` 与 `01`–`04` 四份归档（即本目录）。
- 归档**由项目记忆与决策文档整理而成**，并在每份文档开头标注归档性质；
  未使用（也未曾获得）LearnBuddy 平台的原始对话导出文件，因此**不含逐字对话原文**。
- `README.md` 给出「结果 JSON ↔ 归档章节 ↔ SubAgent 批次」的完整对应表与三条查证路径。

### 3.2 provenance 修正（对应简报 P1「`sourceConversationId` 为合成串、缺 `sourceTurnId`」）

对 `frontend/public/results/` 下 **13 份 JSON** 统一修正：

| 字段 | 修正前 | 修正后 |
|---|---|---|
| `sourceConversationId` | 批次代号，如 `wave3-grading-A` | 归档文件的仓库相对路径 + 锚点，如 `conversations/03-评阅生产与一致性评测.md#批次A` |
| `sourceTurnId` | **全部缺失**（字段不存在） | 填入可查证的批次代号 `wave3-grading-A` / `-B` / `-C` |

- `sourceTurnId` **被 schema 允许**：`frontend/lib/schema.ts` 中 `ReviewProvenanceSchema` 定义为
  `sourceTurnId: z.string().optional()`，且该 schema 的 `.strict()` 只拒绝**未定义**字段，不拒绝这个已定义的可选字段。
- `_example.json` 是契约示例而非真实评阅结果：其 `sourceConversationId` 改为 `conversations/README.md#契约示例`；
  其 `sourceTurnId` **留空**——示例不承载真实轮次，不填任何无法查证的伪轮次标识。
- 每份 JSON 修正后**按契约算法重算 `resultFingerprint`**（13 份全部重算）。

### 3.3 R9 契约违规修复（对应简报 P1，违反 `docs/contract.md` §3 规则 1）

**违规事实**：`sample-11/R9` 与 `sample-12/R9` 的 `evidence` 数组为空，但 `needsReview` 为 `false`。
契约 §3 规则 1 明确：「**证据数组为空**……也应置 `needsReview = true`」。

**修复依据与取值**：

1. `needsReview`：`false` → `true`（契约 §3 规则 1 强制要求）。
2. `confidence`：按契约 §3 的分级表 —— **「未找到有效证据」属 LOW 档 `[0.00, 0.60)`**，
   故下调至 **0.50**（低于契约示例中「低清截图、证据薄弱」所用的 0.58，表达「完全没有可引用证据」）。
3. **档位与得分不做任何改动**：经核对，两份结果的 R9 原本已是
   `level: "notMet"` / `levelScoreRatio: 0` / `score: 0`，且 `deductionReason` 已写明「未找到相关证据：……」，
   已满足契约 §3 规则 4 的「证据不足处理红线」（置未达标档、`score = 0`、扣分理由写明未找到证据）。
   因此**总分 `totalScore` 不变**。
4. 复核记录补充说明：在 `review.triggerReason` 与 `review.opinion` 中按既有措辞风格补充
   「该评分点未找到可引用证据，已标记待教师人工确认」的说明，与契约 §3 规则 3
   （复核后仍低于 0.60 须显著标注并建议教师人工确认）对应。
5. 连带口径同步：`review.overallConfidenceBefore` / `After` 为**各 `ScoreItem.confidence` 的算术平均**
   （契约 §3 规则 5），R9 置信度变化后必须同步重算，否则会引入新的口径违规。
