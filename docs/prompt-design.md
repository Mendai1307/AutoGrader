# Prompt 设计原则

> 本文回答一个问题：**"凭什么相信这五个 Agent 的输出？"**
> 答案不是"模型很聪明"，而是四层工程约束：结构化契约、逐字证据、可机械复算的档位口径、可回溯的审计字段。
>
> 各 Agent 的具体 prompt 规格见 `backend/agents/*.md`；契约权威定义见
> [`contract.md`](contract.md) 与 `frontend/lib/schema.ts`。

---

## 一、为什么用结构化 JSON 契约约束输出

自由文本的评语无法被机器校验，也无法被稳定复现。因此本项目的 Agent 输出被约束为
**一份严格 schema 定义的 JSON**（`ReviewResult`），理由有四条：

1. **可机器校验**：Zod 的 `.strict()` 意味着**未知字段一律拒绝**。
   模型"顺手多加一个 `explanation` 字段"就会被直接拦下 —— 这是防止 AI 自由发挥污染静态资产的硬闸门。
2. **单一真源**：同一份 schema 同时约束三处 —— LearnBuddy 的输出格式、前端的 TypeScript 类型
   （由 `z.infer` 推导，**禁止手写重复 interface**）、仓库内的 JSON 资产。
   口径只有一处，改一处即三处同步。
3. **可复算**：总分、单项得分、权重和都是**纯函数级**可复算的量
   （`computeWeightedTotal` / `verifyItemScore` / `computeItemScore`）。
   因此"AI 给了 97.2 分"这句话是可以被独立验证的，而不是只能相信。
4. **可定位错误**：校验失败时返回的是**字段路径 + 中文说明**（如 `scores.2.confidence: 置信度必须在 0–1 之间`），
   可直接用来要求模型定点重做，而不用整体重生成。

配套的 prompt 级要求（写在每个 Agent 规格的执行步骤里）：

- 输出**一个合法 JSON 对象**，不带解释文字、不带 Markdown 围栏、不带注释；
- 只使用契约定义的字段名（拼写与大小写严格一致）；
- 数值统一：置信度是 **0–1 浮点数**（禁止百分数），分数保留 **2 位小数**；
- 学生身份一律使用**泛指代号**（`学生A`）。

## 二、反幻觉怎么保证（四层防线）

幻觉在评阅场景里最致命的形态是"**编造一段原文当证据**"。本项目用四层约束把它压到最低：

### 第一层：输入层的"允许失败"

Prompt 里显式规定：**找不到就当找不到**。
每个 Agent 规格都有一个"反幻觉约束（红线）"小节，核心是同一条：

> 找不到证据时输出"**未找到相关证据**"，判定为 `notMet`、`score = 0`；
> **严禁编造引用原文、行号、图号。**

这条设计的关键在于**给模型留了合法出口** —— 如果 prompt 只要求"必须给出证据"，
模型在无证据时的最优策略一定是编；明确允许"未找到"，编造才不再是唯一出路。

### 第二层：字段层的"引用必须可回溯"

`Evidence.quote` 被定义为**逐字摘录，不得改写**，且必须同时给出 `location`
（`section` / `lineStart` / `lineEnd` / `figureNo` / `tableNo`，至少一项）。
即"证据"不是一句结论，而是一个**可回原文定位的坐标**。
配合 Parser 提供的行号口径（1-based 闭区间），任何人都能回原文核对。

`kind` 与 `location` 还有交叉约束：`figure` 应带 `figureNo`、`table` 应带 `tableNo`。
项目内样例报告的 `figures/*.png` **未随仓库提供**，因此 Parser 规格明确要求：
"只能依据图题判读，并在 `note` 声明该限制"，且此类证据置信度上限建议 0.70
（实际样例中对应证据取 0.60）。**这是把"看不见的东西"如实标成不确定，而不是假装看得见。**

### 第三层：判定层的"无证据即零分"

`ScoreItem.evidence` 为空数组是**合法状态**，但契约同时规定：
此情形应置 `notMet` 档、`score = 0`、`deductionReason` 写明"未找到证据"（`contract.md` 三.4）。
于是"编造证据"不仅违反 prompt，**在评分上也拿不到任何好处**（有证据才可能得高分，编造会被 Reviewer 与人工复核打回）。

### 第四层：复核层的"不得制造确定性"

Reviewer 的上调门槛被写死：**只有找到可核对的新事实**（数据可互相复算、正文确有引用）
才允许上调置信度；仅凭"看起来合理"不得上调；无法核实就维持低置信或下调，
并写明"建议教师人工核验"。

`sample-01` 的 R7 就是范例：复核后置信度 `0.76 → 0.82`，但档位与得分不变，
并保留"截图真实性建议教师在批阅时人工核验"的提示 —— 复核提升了信心，但**没有伪造确定性**。

## 三、为什么要求"先定档位，再算分"

Grader 的执行步骤被强制为单向链：**判档位 → 取系数 → 算分数**，禁止反向。

### 3.1 反"凑分"

如果允许先给分再解释，模型会天然倾向于给一个"看起来合理"的分（如 85），
然后再补理由 —— 这是奖励导向而非依据导向。先定档位则相反：
必须先回答"证据能支撑到哪一档"，档位确定了，**分数只是它的算术后果**。

### 3.2 让分数可被机械核查

契约把"档位"与"分数"绑定成一条公式：

```
score_i              = round2(maxScore_i × levelScoreRatio_i)      ← 单项
totalScore           = round2( Σ ( score_i / maxScore_i × weight_i ) )   ← 加权总分
```

于是前端可以做两件确定性核查（容差 0.01）：

- `verifyItemScore(item)`：该项得分是否等于"满分 × 档位系数"；
- `verifyTotalScore(result)`：声明的总分是否等于按权重复算的结果。

**只要这两条成立，就意味着"分数不是随手写的"。** 本次整理对 12 份结果 + 1 份契约示例的
全部单项与总分做了复算，13/13 通过（见 [`testing.md`](testing.md) 第二节）。

### 3.3 一条容易踩的坑（已写入 Grader 规格）

`RubricItem.deductionNotes` 描述的是"在档位基础上如何浮动扣分"，
但契约同时要求 `score` 严格等于 `maxScore × levelScoreRatio`。
因此**档位内的浮动不能靠直接改 `score` 实现**，只能通过**选择更低一档**
（或教师在 rubric 中为该点增设一档及其专属 `scoreRatio`）来表达。
Grader 规格里对此有明确禁令："绝不输出与 `levelScoreRatio` 不符的 `score`"。
这两条规则如果被误解，会造成"看着合理但校验必失败"的产出。

### 3.4 加权口径的另一个好处

当教师令 `maxScore_i = weight_i` 时，公式退化为 `totalScore = Σ score_i`，
与"得分直接相加"的直觉一致 —— 教师无需理解公式也能核对结果。

## 四、审计：哪些字段在支撑"可审计、可回溯"

> **先澄清一处口径**：本项目的契约中**不存在 "fp" / "rp" 字段**。
> 已核对 `frontend/lib/schema.ts` 全文（9 个对象全部 `.strict()`）与
> `frontend/public/results/` 下 13 个 JSON 资产，均无此类字段。
> 因此**审计能力并非由 fp/rp 承载**，而是由下面这四组**真实存在**的字段共同承载。

### 4.1 溯源四件套（`provenance`，见 `contract.md` 第五节）

| 字段 | 回答的问题 |
|---|---|
| `resultFingerprint` | 结果**是否被改动过**？（自证完整性） |
| `sourceConversationId` / `sourceTurnId` | **哪次对话、第几轮**产出？（回溯到人证） |
| `generatorAgent` / `generatedAt` | **谁、何时**产出？（责任主体与时间线） |
| `schemaVersion` | 用**哪一版契约**解析？（可复现解析） |

**指纹算法**（可被任何人独立复算）：把整个 `ReviewResult` 对象按**字典序递归排序键**、
将 `provenance.resultFingerprint` **置为 `""`**，序列化为**无空格 UTF-8 JSON**，取 **SHA-256 十六进制小写**，加 `sha256:` 前缀。
指纹不覆盖自身，故计算时必须置空，否则陷入循环依赖。
（实测：13/13 份资产的指纹均可复算出与文件声明一致的值。）

### 4.2 判分留痕

| 字段 | 审计价值 |
|---|---|
| `ScoreItem.deductionReason` | 为什么没得满分；满分时为 `null` —— 空值本身也是可核对的信号 |
| `ScoreItem.evidence[].quote` + `location` | 每条结论的**原文出处**，可逐字回查 |
| `ScoreItem.confidence` + `needsReview` | 该判定的把握程度，以及是否已进入复核 |

### 4.3 复核留痕（`review.adjustments[]`）

`confidenceBefore` / `confidenceAfter`、`scoreBefore` / `scoreAfter`、`changed`
构成一条**显式的改动记录**：

- 未改分时 `scoreBefore = scoreAfter = null`，`changed = false`（仅调整置信度）；
- 改判时填实际数值、`changed = true`，且必须同步新档位的系数与得分，并重算总分。

三个字段的语义被严格区分，正是因为"**只上调置信度**"与"**改动分数**"是两件性质不同的事 ——
前者不改变结论，后者会改变成绩。审计时必须能一眼分清（`sample-01` 的 R7/R12 即属前者）。

### 4.4 过程留痕（`steps[0..4]`）

五个 `ReviewStep` 各自记录 `inputSummary` / `outputSummary` / `confidence` / `note`，
把"每一环拿到了什么、产出了什么、有多少把握、有什么局限"固化成可展示的时间线，
在 `/trace` 与 `/report/[id]` 页面直接呈现。这让"AI 是不是黑箱"这个必被问到的问题有了具体答案。

### 4.5 关于"假阳性 / 假阴性"这类指标

如果关心的是"AI 判错的比例"（通常用 FP / FN 表达），本项目当前用**另一组指标**承担，且是真实计算的：

| 指标 | 口径 | 实测值 |
|---|---|---|
| 总分 MAE | `(1/N) × Σ|AI 总分_i − 教师金标准_i|`，N = 已产出结果的报告数 | **3.05**（N = 12） |
| 逐项档位命中率 | 档位与金标准**完全一致**的评分点数 ÷ 可比评分点数 | **106 / 144 = 0.7361** |
| 最大单份偏差 | `max|AI_i − 金标准_i|` | 14.0（`sample-04`） |

这三项由 `frontend/lib/analysis.ts` 的纯函数在 `/eval` 页面**实时计算**，不是写死的数字。
**尚未实现**的对比指标（如 Cohen's Kappa、置信度校准曲线）在
[`testing.md`](testing.md) 第五节中如实列为"未做"，不做夸大。

## 五、Prompt 结构上的几条工程约定

1. **每个 Agent 规格都包含同一套骨架**：角色定位 → 输入 → 输出（严格对齐 schema）→ 执行步骤 →
   判定规则 → 置信度口径 → 反幻觉约束 → 自检清单。
   "执行步骤"要写到"另一个 LLM 拿着它能复现同样行为"的粒度；"自检清单"用于输出前的自查。
2. **口径只写一处**：置信度分级、档位系数、总分公式一律引用 `schema.ts` / `contract.md`，
   不在 prompt 里另立一套数值（避免三处口径分裂）。
3. **要求量化摘要**：`inputSummary` / `outputSummary` 必须带数字
   （例如"28 条证据：text 17、code 7、table 3、figure 1"），便于人工与机器双向核对。
4. **明确交接物**：每个 Agent 都写清"我交付给下一环什么、以什么形式"，
   避免中间产物在文档里蒸发（例如 Parser 的章节树是**不落盘的工作格式**，这点必须写明）。
5. **允许并记录失败**：`note` 字段被定位为"局限与人工介入提示"的专用位，
   鼓励写入不确定性，而不是把不确定隐藏起来。
6. **版本演进有规矩**：`schemaVersion` 遵循 `MAJOR.MINOR.PATCH`（触发条件见 `contract.md` 第六节），
   rubric 有自己的 `version`，两者相互独立 —— rubric 修订不影响契约版本。
7. **合规约束写进规格本身**：三个 Agent 文档都显式声明"本文件是 prompt 规格、不是代码，
   五 Agent 的执行者是 LearnBuddy"，防止后来者误以为 `backend/` 里有可执行的模型调用逻辑。
