# W2 · 编排形态（单会话分步 / 多会话分环）

> 对应《步骤路径规划书》**1.4.2**：编排形态两种，**两种都要能跑通同一份报告**。
>
> 本文件的判据**不含任何时间估算**——本项目明确「只排步骤路径与依赖，不做工期倒排」。

---

## 一、两种形态

### 形态 1 · 单会话分步（一个对话内顺序跑完五环）

```
一个 LearnBuddy 会话
  └─ Parser → Evidence → Grader → Reviewer → Feedback
     （每环之间在会话内交接，T1–T5 由内置 Bash 以绝对路径调起）
```

| | 内容 |
|---|---|
| 交接方式 | 会话内的上下文（每环输出仍是结构化对象，只是不必落盘） |
| 适用 | 单份报告、结构清楚、一次成型；需要连续推理的场景（如某评分点要反复取证） |
| 固有代价 | 对话越长，上下文压力越大；**任一环失败若要回退，回退范围落在会话内** |

### 形态 2 · 多会话分环（每环一个对话，环间以产物交接）

```
会话 A：Parser   → 产出 t1.json
会话 B：Evidence → 读 t1.json + Rubric → 产出 候选引用 + t3.json + t2.json
会话 C：Grader   → 读上一步产物 → 产出 scores[] + total（T4 复算）
会话 D：Reviewer → 装配 + T5 六项校验 → 产出完整 ReviewResult
会话 E：Feedback → 读完整结果 → 产出 feedback
```

| | 内容 |
|---|---|
| 交接方式 | **文件 / 结构化片段**（见 `W1` §三 的交接物表）。**禁止依赖「上一个会话说过什么」** |
| 适用 | 报告长、结构复杂；需要多人分工或分次推进；某一环要反复重跑而不想动其他环 |
| 固有代价 | 每环都要**独立重建必要上下文**（Rubric、口径、契约）；交接物必须落盘并带校验状态 |

## 二、共同硬约束（两种形态都必须满足）

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **同一份契约** | 形态只是过程差异——产物必须是形状相同的 `ReviewResult`，否则两种形态的产出无法互相替代、也无法统一评测 |
| 2 | **同一套口径** | 总分口径、权重序列、待复核项处理**只在 `../skills/S4-score-calculator.md` 定义一次**；两种形态都不得自行复述或改写 |
| 3 | **每环产物带坐标与置信度** | 环与环之间断掉上下文时，**坐标与置信度是唯一能重建判断依据的东西** |
| 4 | **每环写进 `steps[]`** | `{step, agent, inputSummary, outputSummary, confidence}`——形态不同，**留痕要求相同** |
| 5 | **确定性能力只走脚本** | 两种形态都不得绕过 T1–T5 口算数字或人工判定引用是否忠实（平台侧不存在「开发者注册工具」通道，脚本是唯一承载形态） |
| 6 | **失败必须显式** | 任何一环失败都要落到 `failures[]` / `doubts[]` / `selfCheck` / 状态标记上，不得静默跳过（见 `W3`） |

## 三、选型判据（只看形态特征，不看工期）

| 情况 | 建议形态 | 理由 |
|---|---|---|
| 单份报告、结构清楚、无反复取证 | **单会话分步** | 少一次落盘与重建上下文的开销；推理连贯 |
| 报告长 / 图文混排 / 需要多处反复取证 | **多会话分环** | 每环上下文更短、更聚焦；某环重跑不必重来整链 |
| 由不同人分别负责取证与评语 | **多会话分环** | 交接物是文件，人可以并行推进 |
| 需要向教师展示「过程可见」 | **两种都可以**，但建议**分环** | 分环的中间产物（`t1` / `t2` / `t3` / 校验清单）本身就是过程证据 |
| 契约或 Prompt 刚改过，要做回归 | **单会话分步** | 一条链跑完，便于与 `../evaluations/` 的基线直接比较 |

## 四、两种形态的等价性要求（怎么证明「都能跑通同一份报告」）

**验收方式**：同一份报告、同一份 Rubric，按两种形态各跑一次，然后比对**产物形状**：

1. `steps[]` 都应含五环，`agent` 取值集合相同（`parser` / `evidence` / `grader` / `reviewer` / `feedback`）
2. `scores[]` 的 `rubricItemId` 集合与 Rubric 评分点**一一对应**（不多不少）
3. `totalScore` / `total` 完全一致（同一输入 → 同一口径 → 同一位小数）
4. `provenance.resultFingerprint` **只有在过程性字段被规范化后**才应相同；
   若不同，差异必须能逐项归因到 `steps[]` 的摘要差异——**这是「过程可审计」的直接体现**

> ⚠️ **本项验收需要真实 LearnBuddy 会话**（AI 在对话侧运行）。
> 本工作区只能保证**规格齐备**与**产物形状可校验**（第 1–4 条的判据已写死）；
> 两种形态的实跑对照，须在平台侧对话中完成，届时用 `../tools/T5-contract-validator.md` 逐份校验产物。
