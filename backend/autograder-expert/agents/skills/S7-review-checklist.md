# S7 · 复核与解释

| 项 | 内容 |
|---|---|
| Skill ID | S7 |
| 所属 | **两个入口**：流程 B · 教师复核节点（复核清单）｜模式 3 · 事后追问（解释回放） |
| 对内 Agent | —（教师复核节点与消费侧的 Expert 支持） |
| 对外名称 | 复核 / 解释 |
| 依赖 Tool | **T4 确定性计算器**（入口 A 的排序键就是 T4 `--mode rank`，公式「低置信 × 高出错代价」）。入口 B 不依赖脚本工具，其前置是**读入既有 `ReviewResult` 的通道（R1，✅ 2026-09-26 闭合：走平台内置读取能力）** |

## 目标

把**已经记录的判定与证据**按需要的形式送到教师面前——让教师用最少的时间看到最该看的地方，
并能在事后追问时拿回完整凭据。

一条原则贯穿两个入口：**只呈现事实，永不添加意见。**

## 两个入口

| 入口 | 触发 | 输入 | 输出 |
|---|---|---|---|
| **A · 复核清单** | 流程 B 评阅过程中 | S3 的逐项置信度与疑点；S4 的待复核项与 `W_r` | 排序后的复核清单 |
| **B · 解释回放**（模式 3） | 教师事后追问「为什么这项只有 X 分」 | **已有的 `ReviewResult`** | 该项的判定 + **证据链** + 置信度 + **是否被教师修改** |

两个入口共用一个 Skill，因为方法论相同：**只呈现，不表态。** 差别只在触发时机——A 在评阅流程内，B 在评阅完成之后。

## 执行规则 · 入口 A（复核清单）

1. **只给「哪里需要你看」，不给「你应该怎么判」**——
   不产生任何「专家建议教师改判」的措辞。
2. 排序公式固定（低置信 × 高出错代价），不得随手改。
3. 教师选择不参与复核时，清单**不阻塞流程**；但待复核项仍不计入总分。
4. 只呈现事实（证据 + 疑点 + 置信度），不附过程性解释。
5. 教师若给出终判，结果回灌 S4 重算，再进 S6。

## 执行规则 · 入口 B（解释回放）——三条硬规则

1. **只回放，不重判。**
   只从 `ReviewResult` 中**取出已记录的字段**，按原样呈现。
   **不得新增判断、不得补充理由、不得重新解释**——教师问「为什么」，你答「记录里是什么」。

2. **教师改过的项，不解释原因。**
   若该项的终值来自教师修改（终值 ≠ AI 建议分），只能报「**该项由教师判定**」并附证据链，
   **不得解释为什么是这个分**——那不是你的判断，你没有资格解释它。
   （与 SYSTEM_PROMPT §6.3「教师判断一律高于你、不做解释」一致）

3. **只读。**
   不改分、不改判定、不产生新的 `ReviewResult`、不触发任何重算。
   本入口**没有后置**。

## 常见失败场景

**入口 A**

- 退化成一串无排序的长列表，教师无法判断先看哪一项。
- 夹带「专家认为应当…」这类意见表述，越出禁区。
- 教师选择不参与复核时把流程卡死。
- 把「教师已复核」记录成「结论正确」的背书。

**入口 B**

- **临场编造理由**：教师问「为什么这项低」，Expert 当场构造一个听起来合理、
  但**并非当初判定依据**的解释——例如说「因为你的算法复杂度偏高」，而记录里只写了「证据不足」。
  **这是本入口最高危的失败，也是它唯一真正需要防的事。**
- 解释教师自己改过的项，替教师的判断找理由。
- 顺手「修正」了一个它认为记录有误的判定（违反规则 3）。

## 依赖关系

- 前置：`S3`、`S4`（入口 A）；**已有的 `ReviewResult`**（入口 B）——经 **R1 通道**读入（平台内置文件读取能力，见下）
- 后置：入口 A →（教师参与）回灌 `S4` → `S6`；**入口 B → 无后置（只读）**
- 依赖 Tool：入口 A → **T4 确定性计算器**（`--mode rank`，须逐项提供 `confidence`——缺失会结构化报错，不静默退化）；入口 B → 无

### 两个外部要求（R1 与 R2 均已闭合）

| # | 要求 | 现状 |
|---|---|---|
| R1 | **读入既有 `ReviewResult` 的通道** | ✅ **已闭合**（2026-09-26 用户裁决）：**走平台内置读取能力**。教师给出该 `ReviewResult` 的绝对路径（或把 JSON 内容直接粘进对话）→ 由平台内置的**文件读取**能力逐字读入 → 需要时再用 **T5** 校验其合规性 → 进本入口只读回放。**不新增工具、不扩展 T6**，故「给 T6 加 `result` 类别」这条路**不再考虑**。⚠️ 读入的内容**不得凭记忆复述**——回放的每一条都必须逐字来自该文件 |
| R2 | **契约须逐项同时携带「AI 建议分」与「终值」，并标明是否被教师修改** | ✅ **已闭合**（2026-09-25 契约冻结）：`scores[]` 逐项含 `suggestedScore`（AI 建议分）、`score`（终值）、`overriddenByTeacher`（缺省 `false`）。不变式 I7 由 T5 强制：`overriddenByTeacher === true` ⟹ `suggestedScore` 存在且 ≠ `score`。真源见 `contract/ReviewResult.schema.json` 与 `docs/contract.md` |

R2 已满足，规则 2 可执行——判得出「这项是不是教师改的」，也就能决定该不该解释。
**R1 已满足**：入口 B 的前置从「待定」变为「可执行」——文件路径由教师给出，内容由平台内置的
文件读取能力逐字读入；本入口全程**只读**，无后置。

**终值由谁写入**（与 SYSTEM_PROMPT §7.3 一致）：`suggestedScore` 由 Expert 给出；
`score`（终值）与 `overriddenByTeacher` **不由 Expert 填写**——教师未参与复核时，
由系统取 `suggestedScore` 作为终值。**Expert 不得自行宣布任何分数为终值。**
本入口对这两者**只读，不写**。

**字段名以契约为准**：本 Skill 此前引用的 `items[]` / `pointId` 系暂存稿命名，
冻结后统一为 `scores[]` / `rubricItemId`（`docs/contract.md` 第 3.1 节）。
